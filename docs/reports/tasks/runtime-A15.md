Deviations:
- **`call_api` runs the turn through a new helper `_run_sync(coro)` instead of calling `asyncio.run` directly, because the plan's own test is an `async def` under `asyncio_mode = "auto"`.** Written exactly as the plan gives it, `call_api` raises inside that test: pytest-asyncio has already entered an event loop and `asyncio.run` refuses to nest. `_run_sync` calls `asyncio.run` when no loop is running — promptfoo's case, a fresh synchronous Python process — and otherwise submits `asyncio.run` to a one-worker `ThreadPoolExecutor`, which gets a loop of its own. The provider's public contract is unchanged, `call_api(prompt, options, context) -> {"output": ...}`, and what promptfoo sees is byte-for-byte the plan's. Evidence: a three-line script calling `asyncio.run(asyncio.sleep(0))` from inside `asyncio.run(main())` prints `RuntimeError: asyncio.run() cannot be called from a running event loop`.
- **`.github/workflows/ci.yml` gates the regression suite on `env.GOOGLE_API_KEY != ''` rather than the plan's `secrets.GOOGLE_API_KEY != ''`, and lifts the secret to the job `env`.** GitHub does not expose the `secrets` context to a step-level `if` — the contexts allowed there are `github`, `needs`, `strategy`, `matrix`, `job`, `runner`, `env`, `vars`, `steps`, `inputs` — so the plan's form fails the workflow at parse time with `Unrecognized named-value: 'secrets'`. Setting `GOOGLE_API_KEY: ${{ secrets.GOOGLE_API_KEY }}` at `jobs.test.env` makes it readable by both the `if` and the step, and an unset secret still expands to the empty string, so the intended skip behaviour is preserved exactly.
- **Two additions to that workflow that the plan does not have, both needed for the suite to start at all.** (1) `actions/setup-node@v4` pinned to Node 22 immediately before the promptfoo step: promptfoo now hard-exits on Node below 22.22 before it reads the config, and `ubuntu-latest` does not guarantee that version. Evidence from this machine: `npx --yes promptfoo@latest validate -c promptfooconfig.yaml` -> `promptfoo requires a supported Node.js runtime. Detected: v22.14.0 Required: >=22.22.0`. (2) `PROMPTFOO_PYTHON: ${{ github.workspace }}/runtime/.venv/bin/python` on the promptfoo step: CI installs the project with `uv pip install -e ".[dev]"`, which puts `spatalk` in `runtime/.venv` only, so the bare `python` that promptfoo would otherwise spawn for `file://provider.py` and the nine `file://asserts.py:*` assertions cannot import `spatalk`. Both additions carry the same `if` as the suite, so a run without the secret is unaffected.
- **One test function beyond the plan's, `test_asserts_pass_on_good_turns_and_fail_on_claims`, in the same file.** The plan exercises `asserts.py` only through `npx promptfoo eval`, which cannot run here, so all nine graders would otherwise have shipped with nothing checking them. The new test feeds each grader a synthetic output of exactly the shape `call_api` returns and asserts both directions: a rendered outcome passes; a claimed action (`"You're all set for Thursday."`) fails with `all set` in the `reason`; `band3_gate` fails when `expect_reason` disagrees; `health_context_no_advice` fails on `"That's fine to do with eczema."`. Nothing was weakened — `test_provider_runs_brain_with_memory_ports` is the plan's text verbatim, character for character.
- `provider.py` and `asserts.py` are otherwise the plan's code with module docstrings added and long lines wrapped to the pinned `line-length = 100`; no expression, key name, variable name or string literal differs. `promptfooconfig.yaml` is the plan's text verbatim, including the `transform: "output.text"` placement that Step 6 flags as the first thing to move if the two `llm-rubric` graders error. `pyproject.toml` gained exactly one line, `pythonpath = ["."]` under `[tool.pytest.ini_options]`, as Step 1 asks.

Notes for neighbours:
- **The suite has never been executed. Two things must be true before it can be, and neither is code.** A `GOOGLE_API_KEY` in the environment, and Node >= 22.22 on the machine running it (`node -v` here is v22.14.0, and promptfoo exits on the version check before it parses the config). Run it locally as `cd runtime/scenarios && PROMPTFOO_PYTHON=../.venv/Scripts/python.exe npx promptfoo@latest eval -c promptfooconfig.yaml --no-cache` on Windows, or `../.venv/bin/python` elsewhere. Without `PROMPTFOO_PYTHON` promptfoo spawns the system interpreter, which has no `spatalk`, and every case fails with `ModuleNotFoundError` instead of an assertion failure — that is a wiring failure, not a regression. Expect a 13-row table; exit code 0 means every assertion passed. `CLAUDE.md` caps this at one run per QA gate.
- **Treat the first run as calibration, not regression.** Ten of the thirteen cases are protected by something deterministic: the rules gate fires on `real person`, on `rash`/`swelling`, and — worth knowing — on `is that normal`, which is already in `DEFAULT_LEXICONS["clinical"]`, so the case described in the plan as "clinical phrased without lexicon words (model must escalate)" will in fact escalate through the gate rather than through the model. If that case ever starts failing, it means the lexicon changed, not that the model got worse. The three cases that genuinely depend on the model's choice of tool are the training-course enquiry (needs `capture_request` with `kind=training_enquiry`), the booking link by text (needs `send_booking_link` with a `service_id` that resolves in the bundle), and the goodbye (needs `end_conversation`). If those fail, the fix belongs in `spatalk/brain/prompt.py` or `spatalk/brain/tools.py`. Do not loosen a grader to get green.
- **`asserts.py` encodes the honesty contract as its own word list, deliberately narrower than the runtime guard's.** `BANNED` is six substrings (`booked`, `confirmed`, `is scheduled`, `all set`, `cancelled your`, `rescheduled`); `spatalk/brain/guard.py` owns the real lexicon and it is much larger. The suite is a second, independent check on rendered output — if it imported `DEFAULT_COMPLETION_LEXICON` it would only be testing that the guard agrees with itself. Keep them separate; a word added to the guard does not need adding here.
- **Three assertion strings are tenant wording and will break if `tenants/skincentrix/scripts.yaml` is edited.** `link_sent` looks for `texted` (from `link_sent: "I've just texted you the booking link for {service}..."`), `ended` looks for `Thanks for calling` (from `goodbye`), and the cancellation case's `icontains` looks for `confirm with you` (from `captured`). All three match `docs/reference/tenant-config.md` lines 75-79 today. `SCENARIO_TENANT` selects the bundle, but these assertions are Skincentrix-specific, so another tenant needs its own cases.
- **The provider builds its own world and deliberately does not import `spatalk.http.app`**, per the note runtime-A14 left for this task. It touches no Postgres, no Slack and no Telnyx: `MemoryLedger` + `MemorySms` + `TierCCapabilities`, one fresh set per turn, so `items` and `sms_sent` describe exactly that one turn. It uses `SystemClock`, not a fixed clock, so the `confirm_by` wording in a reply moves with the wall clock and the business calendar. Never assert on a specific time in a case; assert on `items[].urgency`, as the graders do.
- **Task 16 (deploy): this workflow does not build an image, does not push, and does not run Alembic.** It installs, lints, runs pytest against a Postgres service container, and optionally runs the regression suite. A build or deploy gate should be a second job with `needs: test` rather than an extension of this one. If Task 16 adds `runtime/.dockerignore`, note that it must not break `ruff check spatalk tests scenarios`, which runs against the checkout rather than the image, so excluding `scenarios/` from the image is fine but removing it from the repo is not.
- **CI's Postgres is on 5432; this machine's compose maps 5434.** `runtime/docker-compose.yml` publishes `5434:5432` and `tests/conftest.py` defaults `TEST_DATABASE_URL` to `...localhost:5434/spatalk_test`, while the workflow sets that variable explicitly to `localhost:5432`. Both are right for their environment and the explicit CI value wins over the conftest default. Do not "fix" one to match the other.
