Deviations:
- **`CLAIM_SQL` matches `state = 'queued' AND (run_at <= :now OR run_at = created_at)`, where the plan had only `run_at <= :now`.** `enqueue` leaves `run_at` to the column's server default (`now()`, as `data-model.md` specifies), so an "immediately due" job is stamped with the *database* clock while `run_once` compares against the *application* clock. Under `FixedClock` the two disagree by a day, and the plan's predicate claims nothing, so `assert await jobs.run_once(sf, ctx) == 2` could never pass. Both `run_at` and `created_at` default to the same transaction timestamp, so `run_at = created_at` is an exact marker for "no run_at was ever set, run it now", and every explicitly scheduled job keeps the plan's application-clock semantics (a retry backed off to `now + 30·2^attempts` is not re-claimed until the clock reaches it, which is what the dead-letter half of the test exercises). Evidence: `uv run python` against `spatalk_test` after one `enqueue(sf, "test.ok", {"n": 1})` -> `db now(): 2026-09-02 05:33:16+00:00 / fixed_clock.now(): 2026-09-01 18:00:00+00:00 / plan predicate claims: 0 / shipped predicate claims: 1`.

Notes for neighbours:
- **Handlers register on import, not on app start.** `deliver.slack`, `deliver.email` and `digest.email` are registered by the `@jobs.register_handler` decorators at the top level of `spatalk/ledger/delivery.py`. A process that never imports that module has an empty registry and every delivery job fails with `no handler for deliver.email` until it dead-letters. **Task 14's `create_app` must import `spatalk.ledger.delivery`** (importing `spatalk.ledger.scheduler` is enough, since it imports delivery) before starting the worker task.
- **Task 14, `create_app(ctx, start_background=False)`:** the two routers need nothing but `app.state.ctx = ctx` and `app.include_router(...)`; they read `ctx.settings`, `ctx.ledger`, `ctx.registry`, `ctx.clock` and `ctx.sf` only. I verified both routers against the plan's own `tests/test_http_actions.py` assertions using a throwaway `FastAPI()` that did exactly that (plus a transcript-link case): 4 passed, including the `404` on `/a/not-a-token`, the `401` on a bad Slack signature, and `state == "resolved"` after a valid one. The throwaway file was deleted and is not committed, so `tests/test_http_actions.py` stays red until `spatalk/http/app.py` exists — that is the plan's stated expectation, not an unknown failure.
- **Task 10 job counts.** For Skincentrix (`destinations: email info@skincentrix.com, slack SKINCENTRIX_SLACK_WEBHOOK`), a normal item enqueues 2 jobs; `escalation=True` enqueues 3 — one per destination plus a second email to `cfg.escalation.owner_email` — and only the escalation path prefixes `"ESCALATED, past due: "` onto the subject and the Slack fallback text. That is exactly the `1 slack / 2 emails, all subjects contain ESCALATED` that Task 10's test asserts. `urgent_only` destinations are skipped unless the item is urgent **or** it is an escalation.
- **Delayed jobs and fake clocks.** `enqueue(sf, kind, payload, run_at=<future>)` is due only when `ctx.clock.now()` reaches `run_at`; `enqueue` without `run_at` is due immediately whatever the clock says. A later plan that schedules work into the future (the text-channels follow-up, `sms.textback`) can therefore test "not yet due" with `FixedClock` as long as it passes an explicit `run_at`; it must not rely on a defaulted `run_at` being in the future.
- **Retries and the dead letter.** A handler exception increments `attempts`, records `TypeName: message` (truncated to 2000 chars) in `last_error` and backs the job off to `now + 30·2^attempts` seconds; at `attempts >= max_attempts` (5) the job goes `state = 'dead'` and is logged at error level. Nothing retries a dead job; there is no automatic alert on one yet (that is the operations plan).
- **One transaction per `run_once` batch.** The claim, every handler call and the state write share a single session opened with `FOR UPDATE SKIP LOCKED`, so two workers never take the same job — but a handler must open its own session for its own reads and writes (`ctx.ledger.get`, `ctx.registry.get` already do). A handler that tried to update `runtime.jobs` itself would deadlock against the batch's own row locks.
- **The action link carries the action.** `build_links` signs three separate tokens (`ack`, `resolve`, `transcript`) for the same item; `GET /a/{token}` never mutates anything — it renders a confirm form for `ack`/`resolve`, or the transcript for `transcript` — and only `POST` acts, so a mail scanner prefetching the link cannot acknowledge an item. `flows.md` §2 step 4's audit write lives here: `POST /a/{token}` writes an `audit_log` row with the typed-in actor, and the transcript view writes `read_transcript` with actor `link`. `spatalk/http/slack.py` writes no audit row — Slack's `user.username` is recorded on the item as `acknowledged_by`/`resolved_by` instead; if the portal plan needs a Slack audit trail, that is a one-line addition there.
- **Nothing in this task can claim an outcome.** `delivery.py` and both routers import no `spatalk.brain.outcomes` name, render no caller wording, and put only structured item fields (`TYPE_LABELS[type]`, contact fields, `preferred_window` keys, `humanize_due(...)`) into Slack and email — the transcript is reachable only behind a signed link. `items` still has no free-text column.
