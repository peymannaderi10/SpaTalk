## What the shell is

`AppLayout` is the kit's `authenticated-layout` arrangement: `SidebarProvider` → `SearchProvider` → `AppSidebar` → `SidebarInset` carrying `Header` and `Main`. The inset carries `@container/content` (R0's note) plus `has-[[data-layout=fixed]]:h-svh` so a page that asks `Main` for `fixed` scrolls inside the shell rather than scrolling the shell.

It imports nothing from Wasp. Everything that knows about a person, an organisation or an operation is a prop: `context`, `sections`, `breadcrumbs`, `orgSwitcher`, `profile`, `actions`, `paletteOpen`/`onPaletteOpenChange`, `fixed`, `fluid`. That is what lets `AppLayout.test.tsx` mount the whole shell — sidebar, header, breadcrumbs, palette and all — in jsdom under a `MemoryRouter`, and it is why the two shells (an organisation's and the agency's) are one component rather than two that drift.

`OrgAppLayout` is the single Wasp-connected wrapper: `useAuth`, `listMyOrganizations`, `logout`, and the two palette queries. Nothing else in the portal has to know how the shell is fed.

## Settings tabs

`SettingsPage` held its tab in `useState`. It now reads `useSearchParams().get("tab")` and writes it back with `setSearchParams(..., { replace: true })`. The slugs are the labels lowercased — the same eight `nav.ts` already points at — and `tabSlug`/`tabFromSlug` are the only two places that has to be true. The default with no parameter is `Hours`, as it was.

One addition beyond a plain read: a URL with no `tab` at all is rewritten (replace, not push) to `?tab=hours`. Without it the page shows Hours while no Setup item in the sidebar is marked, because `isActive` — R0's — insists the query match where several items share a path. The tab content, the field ids, the validation and every testid inside the tabs are untouched, and the in-page tab buttons stay, so `client.spec.ts`'s `getByRole("button", { name: "Versions" | "Numbers" })`, `sms-blocks.spec.ts`'s and `integrations.spec.ts`'s all still work; they now change the URL as well as the tab.

## Deviations

- **`qa-gate-b.spec.ts` was edited.** It drove the organisation switcher as `getByLabel("Organisation")` → `locator("option")` → `selectOption` → `toHaveValue`. That `select` lived in the marketing navigation bar, which no longer renders over `/app/:orgSlug` pages, so those three assertions now click `org-switcher`, read `getByRole("menuitem")`, click `org-switcher-<slug>` and assert the trigger's text. What they prove — two organisations offered, the third never, picking the other one lands on its pages — is unchanged, and `aria-label="Organisation"` came across onto the new trigger so the first `getByLabel` still resolves. The plan's file list permits exactly this: e2e specs "unchanged unless a selector was on a removed element". This is the only spec edited.
- **`App.tsx` now gives `/app/:orgSlug/*` the bare `Outlet` the admin routes already had.** Not in the task's file list. Without it every page in an organisation would carry the marketing navigation bar — a second organisation switcher, a second theme toggle and a second user menu — stacked above the sidebar shell, inside a `max-w-(--breakpoint-2xl)` wrapper that would have squeezed it. `/app` itself (the list of organisations) still gets the bar.
- **Two pages read a new query parameter, which "nothing else about the pages changes" did not anticipate.** The palette is required to "open a request by number" and "open a conversation by phone", and both need somewhere to land. `RequestsPage` reads `?item=<id>`: it selects the tab the request is filed under and scrolls its card into view, once, guarded by a ref. It deliberately does **not** open the transcript, because reading one is an audited act and nobody asked for it yet. `ConversationsPage` reads `?conversation=<id>` and opens it, which is exactly what clicking its row does, audited read included. Both use operations those pages already run. The alternative was a palette entry that promised something it could not do, which non-negotiable 1 rules out.
- **The palette lists what exists rather than parsing what you type.** "By number" and "by phone" are matched by cmdk against entries built from `getTenantRequests` and `getTenantConversations` — the existing operations, no new ones — so a number no request carries offers nothing to select. Both queries are `enabled: paletteOpen`, so a page that has nothing to do with either (billing, people, settings) costs nothing until someone presses ⌘K. Making that possible needed `SearchProvider` to accept a controlled `open`, which R0 had only given to `CommandMenu`.
- **`src/admin/layout/Sidebar.tsx` and `Header.tsx` are deleted.** They were the admin's bespoke chrome and nothing imports them any more (`grep -rn "layout/Sidebar\|layout/Header"` over `src` returns nothing). Leaving two orphaned files that still `import { Activity, Building2 } from "lucide-react"` would have made R3's "no file imports lucide-react" test fail against dead code.
- **`AppLayout.test.tsx` stubs `window.matchMedia`.** jsdom 27 does not implement it and `useIsMobile` calls it on mount. The stub answers "not mobile", which is the desktop shell the unit tests are about; the mobile sheet is proved in `shell.spec.ts`, in a real browser at 390 px.
- **`SidebarInset` and `Main` are both `<main>`.** That is the kit's own arrangement — the registry's `SidebarInset` is a `<main>` and so is the kit's `Main` — and diverging from either vendored component to fix the duplicate landmark seemed worse than leaving it for R4's accessibility pass, which the plan already schedules. Nothing in either suite selects by that role.
- **The admin shell's `NavContext` has an empty `orgSlug`.** `/admin` is not about one organisation, so there is no slug to substitute and no switcher; the Platform items' routes contain no `:orgSlug`, and `platformSections` drops every section that would need one. The brand block (`platform-mark`) stands where the switcher stands elsewhere.
- **`nav.ts` grew `PLATFORM_SECTION` and `platformSections`**, which the task's Produces block does not name. The admin shell has to ask for one section by name; a string literal in `DefaultLayout.tsx` would have been the same coupling without a test on it. `nav.test.ts` gained the two tests the task allows ("extend `nav.test.ts` if the model changes").
- **Prettier was not run**, following R0, N2 and L2: no config file, no format script, no CI step. Files written by hand follow the repository's style; the vendored files keep theirs.
- **`wasp build`, `wasp start`, `wasp test`, `wasp db` and `wasp compile` were not run.** Types were checked with `tsc` against `tsconfig.src.json` emitting to `/tmp`, never into `.wasp/`; the stylesheet with the standalone Tailwind v4 CLI; the tests with Vitest through WSL node as N2 documented. The founder's dev server was not restarted and does not have these edits.

## Notes for R2

- **The layout props every page now gets.** A page inside an organisation is a child of `OrgAppLayout`, which takes `{ orgSlug, orgName?, role?, breadcrumbs?, fixed?, fluid? }`. `OrgShell` passes `breadcrumbs={[{ label: title }]}` and neither `fixed` nor `fluid`, so every page today is the default: a reading-width column capped at `max-w-7xl` by the container query. **A table page should ask for `fixed`** (fills the shell, scrolls inside itself) and **a wall of cards for `fluid`** (drops the width cap) — both are one prop on `OrgShell`'s `Frame`, which is where to add a pass-through when Conversations becomes a `DataTable`.
- **The page still renders its own `h1`.** `OrgShell`'s `Frame` renders `<h1>{title}</h1>` above the content because `client.spec.ts` asserts `getByRole("heading", { name: "Overview" | "Conversations" | "Requests" | "Settings" })` and `qa-gate-b` asserts the organisation's name as a heading on `/app/:orgSlug`. If R2 moves to the kit's page-header block, the accessible name of those headings has to survive.
- **Two pages needed a wrapper of their own**: `OrgHomePage` and `PeoplePage` each keep a local `PageShell({ slug, org, children })` that renders `OrgAppLayout`. They do not go through `OrgShell` and so have no subscription banner and no `Problem`; if R2 unifies them onto `OrgShell`, that is a behaviour change to think about, not a refactor.
- **The palette is where "actions" go.** `AppLayout` takes `actions: CommandAction[]`, and `OrgAppLayout` builds the Requests and Conversations entries. If R2 gives a page something else worth reaching by keyboard, add it there rather than inventing a second palette.
- **`?item=` and `?conversation=` are now part of those two pages' contract.** A restyled Requests page still has to have an element with `id="request-<id>"` to scroll to, or the deep link goes quiet; a restyled Conversations page still has to open a transcript for `?conversation=`.
- **`isActive` decides the highlight** (`sidebar-nav.tsx`, R0's, exported and now exercised by `shell.spec.ts` through `data-active`). It matches on `location.pathname` exactly, plus every key of the item's own query. `/app/:orgSlug/settings/people` therefore never lights up a Setup item, and `?tab=` is what separates the eight.
- **`Header` is `sticky top-0`, not fixed**, so page content flows under it normally; the kit's `header-fixed` marker class has no rule in this stylesheet and nothing depends on one.
- **Screenshots are owed, light and dark, for every page this task touched** — which is every page under `/app/:orgSlug` and every page under `/admin`. They are the orchestrator's after `stop-portal.sh` / `start-portal.ps1`, along with `npm run e2e`, which is the first time `shell.spec.ts` runs.
- **Not committed, and not this task's:** nothing. Everything was staged by explicit pathspec.
