Deviations:
- **`create_app` attaches the three routers with a new local helper `attach_router(app, router)` instead of `app.include_router(...)`, because FastAPI 0.141.1 made `include_router` lazy.** It now appends one opaque `fastapi.routing._IncludedRouter` object to `app.routes` and resolves the real routes only at request time, so the plan's own test line `paths = {r.path for r in app.routes}` raised `AttributeError: '_IncludedRouter' object has no attribute 'path'` and `/telnyx/texml`, `/a/{token}` and `/slack/interactions` were invisible to any inspection of `app.routes`. `attach_router` extends `app.router.routes` with the router's already-built routes and bumps the route-version counter if the installed FastAPI has one. This is behaviour-preserving here: none of the three routers uses a prefix, tags, dependencies or `Depends` anywhere (`grep -rn "Depends\|@router\." spatalk/` -> only the four bare `@router.get/post` decorators), and `response_class=HTMLResponse` on the two `/a/{token}` routes is baked into the `APIRoute` object itself, so it survives. Evidence: `uv run python -c "import fastapi, starlette, inspect, fastapi.routing as fr; print(fastapi.__version__, starlette.__version__); print(inspect.getsource(fr.APIRouter.include_router)[-500:])"` -> `0.141.1 1.6.0` and `self.routes.append(_IncludedRouter(original_router=router, include_context=include_context)); self._mark_routes_changed()`. There is no keyword on `include_router` that restores the eager copy. Verified afterwards that the assembled app is fully intact: `uv run python -c "from spatalk.http.app import create_default_app; a=create_default_app(); print(sorted({r.path for r in a.routes})); print(a.openapi()['paths'].keys())"` -> `['/a/{token}', '/docs', '/docs/oauth2-redirect', '/healthz', '/openapi.json', '/redoc', '/slack/interactions', '/telnyx/texml', '/ws/{token}']` and `dict_keys(['/telnyx/texml', '/a/{token}', '/slack/interactions', '/healthz'])`, so routing, OpenAPI and the docs pages all still see the routes.

Notes for neighbours:
- **Task 15 (CI) — `attach_router` is the thing to watch if FastAPI moves again.** If a future FastAPI restores eager `include_router`, `attach_router` keeps working unchanged (it never depended on the lazy behaviour). If a future FastAPI stops exposing `_mark_routes_changed`, the `getattr` guard already handles that. The only scenario that breaks it is a router that needs a prefix, tags or shared dependencies; the moment any plan adds one (the text-channels and Instagram plans both add routers), that router must go through `app.include_router(...)` instead, and whatever inspects `app.routes` must be taught about `_IncludedRouter`. Pin `fastapi` in CI if you want this stable.
- **Task 15 — `scenarios/provider.py` must not import `spatalk.http.app`.** It builds its own memory-port context (`MemoryLedger`, `MemorySms`, `FakeLLM`); importing `app.py` drags in `spatalk.voice.pipeline`, which imports Pipecat and the Google service, and the scenario runner has no reason to pay that ~1.3 s import or to need a `GOOGLE_API_KEY`-shaped environment. `build_context` is production wiring only.
- **`create_app` does not own a database migration step.** It builds an engine and never touches the schema. Deployment (Task 16) must run `uv run alembic upgrade head` before starting uvicorn, and the CLI's `tenant import` assumes the schema already exists.
- **`build_context` uses `SystemClock`, so every `FixedClock` seam in the suite lives above it.** Anything that needs a deterministic clock builds its own `JobContext` (as both this task's test and `tests/test_http_actions.py` do); there is no way to inject a clock through `build_context`, deliberately, so production cannot accidentally run on a frozen clock.
- **Job handlers register by import side effect, and `app.py` is what guarantees they are all present.** Importing `spatalk.ledger.delivery` registers `deliver.slack`, `deliver.email` and `digest.email`; `spatalk.ledger.scheduler` enqueues those kinds. A new job kind added by a later plan must be imported from `app.py` (or from a module `app.py` already imports) or `run_once` will fail it with `no handler for <kind>` and retry it to `dead` after five attempts.
- **The worker and the scheduler run inside the API process, one of each.** `run_worker_forever` polls every 2 s and `run_scheduler_forever` every 60 s, both wrapped in `try/except` that logs and continues, so a database blip does not kill either loop. If Task 16 ever runs more than one uvicorn worker process, each process gets its own pair; the job claim is `FOR UPDATE SKIP LOCKED` so that is safe for jobs, but `send_digests` guards on `tenants.last_digest_date` inside the same transaction, so it is safe too. Nothing here requires a single process today, but a separate worker container (an operations-plan option) would want `start_background=False` on the API app.
