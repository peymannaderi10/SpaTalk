Notes for neighbours:
- **Task 5 (renderer).** `Captured` carries an extra field the Interfaces block does not mention: `item_type: str` (the ledger `items.type` value, e.g. `callback`, `escalation_clinical`, `send_link`). Use it if the renderer ever needs to vary wording by item kind; `render` as specified does not have to. `confirm_by` is an **aware UTC** datetime straight out of `BusinessCalendar.due_for`, so the renderer must call `humanize_due(out.confirm_by, now, cfg.timezone, urgent=out.urgency == "urgent")` — it must not format the datetime itself, or a Toronto caller hears a UTC time.
- **Task 5 (renderer), `Refused`.** `reason` is exactly `out_of_scope | payment | no_contact | unknown_service | unavailable`, which lines up one-for-one with the `refuse_*` scripts plus `payment`. Tier C only ever emits `unknown_service` and `no_contact` today; `out_of_scope`, `payment` and `unavailable` are for the rules gate (Task 6) and the driver (Task 12) to construct.
- **Task 5 (renderer), `LinkSent`.** It carries `service_id` and `url` but no service *name*; the renderer must resolve the name with `cfg.service(outcome.service_id).name` to fill `{service}` in `scripts.link_sent` / `scripts.link_shown`.
- **Task 8 (`PgLedger`).** The port contract is `async create_item(self, ref: ConversationRef, draft: ItemDraft) -> ItemRecord`, and `ItemRecord.id` is the short number staff quote (`#4821`), i.e. the serial primary key, not a UUID. `MemoryLedger` computes `due_at` itself via `BusinessCalendar(ref.tenant).due_for(draft.urgency, clock.now())`; `PgLedger` must do the same so the fake and the real ledger cannot drift. `MemoryLedger` numbers items from 1 per instance, so tests that assert on `#<id>` should not assume database ids.
- **Health context propagates at the capability layer, not the tool layer.** `TierCCapabilities._capture` force-sets `draft.health_context = True` whenever `ref.health_context` is true, so once the voice/text session flips the conversation-level flag (Task 13 / Task 12), *every subsequent item* in that conversation is flagged without the model being involved. Tool handlers therefore do not need a health-context argument, and the tool schemas (Task 11) must not grow one — the detail stays in the transcript, per CLAUDE.md non-negotiable 2.
- **Caller id fills the contact.** `_with_caller` copies `ref.caller_phone` into `contact.phone` when the model did not supply one. On `channel="chat"` (and Instagram/Messenger) `caller_phone` is `None`, so `send_booking_link` with an empty `ContactInfo` returns `Refused(reason="no_contact")` rather than filing an item — the chat path (B4) must ask for a contact, exactly as `docs/reference/flows.md` §4 step 2 says.
- **`Capabilities` is a plain `typing.Protocol`, not `@runtime_checkable`.** `isinstance(caps, Capabilities)` raises `TypeError: Instance and class checks can only be used with @runtime_checkable protocols`. Type-check structurally; do not assert with `isinstance`. Evidence: ran it, got that exact error.
- **`load_capabilities` raises `ValueError(f"unknown fulfilment {cfg.fulfilment}")` for anything but `tier_c`,** and imports `TierCCapabilities` lazily inside the branch so `capabilities.py` stays importable from a Tier A module later without a cycle. Task 14's assembly should call it once per tenant config version.
- **Flagged for the orchestrator, not fixed here.** The booking-link SMS body is the one piece of customer-facing fixed wording this task builds in code rather than reading from tenant `scripts`: `f"{tenant.name}: here is the booking link for {service.name}: {service.booking_url}"` (plan Step 7, kept verbatim). `docs/reference/tenant-config.md` has no script for an SMS link body — the nearest is `link_shown`, which the reference marks as "chat, Instagram, Messenger" — so there is no reference key to read and no reference/plan conflict to resolve, but a tenant cannot currently edit this sentence. It contains none of the banned completion words (`booked`, `confirmed`, `scheduled`) and is not model-generated, so no non-negotiable is broken. If the intent is that every customer-facing sentence is tenant-editable, the fix is a new `scripts` key (say `link_sms`) in Task 2's `Scripts` model plus a `render_script` call here, which would touch two other tasks' files; I did not do it unilaterally.
- **`ConversationRef` embeds the whole `TenantConfig`** (frozen pydantic model, `arbitrary_types_allowed=True`). It is cheap to pass around but it is *not* hashable — `TenantConfig` contains lists and dicts — so do not use a `ConversationRef` as a dict key or put it in a set despite `frozen=True`.
