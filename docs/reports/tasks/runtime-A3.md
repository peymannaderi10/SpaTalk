Notes for neighbours:
- Every method returns an **aware UTC** datetime (`.astimezone(timezone.utc)`), including `next_open` when the clinic is already open (it returns the instant passed in, converted). Callers that want tenant-local wall time must convert with `ZoneInfo(cfg.timezone)` themselves. Nothing here ever returns a naive datetime, and passing a naive one in will raise from `astimezone`, which is intended (CLAUDE.md non-negotiable 8).
- `due_for("urgent", at)` is deliberately wall-clock: `at + escalation.urgent_minutes`, ignoring opening hours entirely, so an urgent item created at 23:00 is due at 23:15 the same night. Only `"normal"` walks the calendar. This matches `docs/reference/data-model.md` (`items.urgency`: normal = `standard_business_hours` business hours, urgent = `urgent_minutes` wall clock). Task 8's `PgLedger.create_item` should call `due_for` and store the result directly; do not re-round it.
- `humanize_due` produces exactly four shapes: `"within N minutes"` (urgent, `N = max(1, round(minutes))`, so a due time already in the past reads `"within 1 minutes"` rather than a negative), `"by 1:00 p.m. today"`, `"by 1:00 p.m. tomorrow"`, `"by 10:00 a.m. on Thursday"`. Task 5's renderer should pass this string straight into the `{confirm_by}` placeholder — it is already a complete adverbial phrase and needs no leading preposition. Beyond seven days out the weekday name is ambiguous ("on Thursday" could be next week); no current caller can produce that, since `standard_business_hours` defaults to 3 and the calendar never skips more than the holiday list, but a tenant with a long holiday block could.
- The `a.m.`/`p.m.` spelling (lowercase, with periods) and the 12-hour clock with no leading zero are what the voice TTS reads out; changing them changes what a caller hears. Do not "normalise" to `AM`/`PM` in the renderer.
- `BusinessCalendar` reads `cfg.hours`, `cfg.holidays`, `cfg.timezone` and `cfg.escalation` only, and holds no clock: pass the current time in. Construct one per tenant config version; it is cheap and stateless, so Task 4's `TierCCapabilities(ledger, sms, calendar_factory)` can build one per request without caching.
- DST: `add_business_hours` does wall-clock arithmetic inside a day's span, so a span that straddles a Toronto spring-forward or fall-back gap would land on a non-existent or ambiguous local time and be resolved by `fold=0`. No tenant span in the Skincentrix bundle comes near 02:00, so no current configuration can hit it. Worth a test if a tenant ever configures overnight hours.
- `_spans_on` still calls `cfg.hours.get(key, [])` although Task 2's validator guarantees all seven weekday keys exist. Harmless, and it keeps the calendar usable against a hand-built `hours` dict in a test.
