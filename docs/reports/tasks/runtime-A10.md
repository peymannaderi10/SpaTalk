Notes for neighbours:
- **Task 14 (application assembly):** the scheduler is one coroutine, `run_scheduler_forever(ctx)`, and it needs exactly the same `jobs.JobContext` the worker takes. Start it as a second background task alongside `jobs.run_worker_forever(sf, ctx)`; it never returns and swallows its own exceptions, so a crash inside one tick logs and the loop continues. It must not be started twice against one database: `escalate_breached` reads and marks in two separate transactions, so two schedulers can both see the same breached item and deliver it twice. One process owns it.
- **`escalate_breached` only enqueues.** It calls `schedule_item_delivery(..., escalation=True)` and marks `items.escalated_at`; nothing is actually sent until the job worker runs. A deployment that runs the scheduler without the worker will silently mark items escalated and never deliver them.
- **The escalation fan-out is Task 9's, not this task's.** `escalation=True` makes `schedule_item_delivery` ignore every destination's `urgent_only` flag and append one extra email to `cfg.escalation.owner_email`; the `deliver.slack` / `deliver.email` handlers prefix `ESCALATED, past due: `. For the Skincentrix bundle (one email destination, one Slack destination) that is 1 Slack message and 2 emails per breach, which is what the task's test pins.
- **Digest idempotency is a column, not a job dedupe.** `tenants.last_digest_date` is written in the same transaction that enqueues `digest.email`, so a second `send_digests` in the same tenant-local day returns 0. It compares against the date in the *tenant's* timezone, not UTC. Whoever adds a second tenant in another timezone gets correct per-tenant behaviour for free; whoever resets that column re-sends a digest.
- **`send_digests` calls `ctx.registry.get()` while holding an open transaction on `runtime.tenants`.** That takes a second pooled connection per tenant on a cold registry cache. Fine at one or a handful of tenants and with the 30 s registry TTL; if the tenant count grows past the connection pool, hoist the config loads out of the transaction.
- **The digest body comes from Task 9's `digest.email` handler**, which mails every `kind: email` destination (not the owner, unless the owner is also a destination) with subject `<name> front desk: morning digest`. `send_digests` decides *when*, not *what*.
