## Where the label comes from

`scripts.notes_label`, read through the existing `getTenantSettings` query, which both pages now run once per page (never per card) and which shares its react-query cache with the settings page. `notesLabel` takes that configuration and returns the tenant's wording; `DEFAULT_NOTES_LABEL` is the fallback, used only while the query is in flight, when it fails, or when a runtime that predates call notes answers without the script. Neither page shows that query's failure: the label has a default, and the requests are what the page is for.

## Deviations

- **`wasp test client run`, `wasp build` and `wasp compile` were not run.** All three regenerate `.wasp/out` and would have killed the founder's running dev server, which is what happened during Task L2. The client unit tests were run with Vitest directly against the project's own `vite.config.ts` — the same test files `wasp test client` collects — and the compile was verified from the dev server's log instead. The plan's "`wasp build` succeeds in WSL (never while the founder's dev server runs)" is deferred to whoever next has the server stopped.
- **The tests run through WSL's node, not the Windows node.** `portal/node_modules` was installed under WSL, so the Windows node cannot start Vitest: `Error: Cannot find native binding … Cannot find module '@rolldown/binding-wasm32-wasi'`. Fixing that means `npm i` on Windows, which would rewrite `node_modules` and `package-lock.json` under the running server. Command used: `wsl -e bash -lc "export PATH=$HOME/.nvm/versions/node/v22.23.2/bin:$PATH; cd /mnt/c/…/portal && node node_modules/vitest/vitest.mjs run"`. No vitest config was added; the project's `vite.config.ts` already collects these files.
- **A project-wide `tsc -p tsconfig.src.json` still reports three errors, and all three are the stale Wasp SDK, not this code.** They are `src/client/RequestsPage.tsx(196,29)`, `src/client/RequestsPage.tsx(345,29)` and `src/client/ConversationsPage.tsx(298,29)`, each `error TS2339: Property 'notes' does not exist`. The pages' types resolve through `.wasp/out/sdk/wasp/src/runtime/client.ts`, which is a **copy** Wasp refreshes only when it compiles: that copy is dated `2026-09-03 15:07:04`, predates Task N1's contract, and `grep -c "Notes"` on it returns `0`, while the committed `src/runtime/client.ts` has all three fields. Refreshing it means running the Wasp compiler, which this task must not do. The regenerated client was type-checked on its own instead — a scratch file assigning `ItemOut["notes"]`, `ConversationFull["notes"]` and `ConversationFull["notes_at"]` to `string | null | undefined` compiles with `tsc --noEmit --strict`, exit 0 — so the three errors clear the moment the founder's next `wasp start` copies `src` into the SDK. The project typecheck was run with `--outDir /tmp/spatalk-tscheck`, never into `.wasp/out/user`.
- **The block is a shared component, `src/client/CallNotes.tsx`, which the plan's file list does not name.** There are three call sites across two files (the card, and each page's transcript drawer); repeating the markup three times would have let the label, the empty case or the `whitespace-pre-line` drift apart between them. It is the only new file.
- **Two testids, not one.** `data-testid="request-notes"` is the plan's and is on the card. The two conversation-level blocks use `conversation-notes`, because on the requests page a card and an open drawer are visible at once and two elements with the same testid make a Playwright locator ambiguous under strict mode.
- **The notes label is fetched with `getTenantSettings`, a 41 KB response** (`POST /operations/get-tenant-settings 200 … - 41793` in the dev log), most of it the tenant-config JSON schema and the version history that the settings forms need and this page does not. It is one request per page mount, shared with the settings page's cache, and it was chosen over hard-coding the words because the label is the tenant's and a tenant can reword it under Settings, Scripts. If it ever shows up in the requests page's latency, the fix is a thin runtime-config read inside `getTenantRequests` rather than a wider default in the portal.
- **`e2e-tests/tests/client.spec.ts` was not touched.** The plan allows editing it only if it pins the card layout; it pins `request-row` counts, the acknowledge/resolve testids and `transcript-drawer`, all unchanged, and `seed_runtime.py` writes no notes, so no seeded card gains a block.
- **Prettier was not run**, as in Task L2: no CI step runs it, `RequestsPage.tsx` and `ConversationsPage.tsx` were already not clean, and reformatting would churn lines this task did not change.

## Notes for neighbours

- The requests and conversations pages now issue `getTenantSettings`. Anyone counting runtime calls in an e2e test, or thinking of gating that operation on an owner role, has to account for it: it is called by every member who opens either page.
- Nothing renders when `notes` is null, including no heading — a conversation with `notes_at` set and `notes` null is an honest "we drafted and there was nothing to pass on", and it looks exactly like a conversation nobody drafted.
