Notes for neighbours:
- **Task 12 (`driver.py`):** `to_genai_declarations(build_tools(cfg))` is accepted verbatim by the installed google-genai — `types.Tool(function_declarations=[types.FunctionDeclaration(**x) for x in d])` builds all five declarations with the right names. Do not re-wrap or re-key the dicts. Evidence: that exact snippet printed `genai Tool OK 5`.
- **Task 12/13:** `to_genai_declarations(tools)[i]` is exactly `tools[i].to_default_dict()` on Pipecat 1.8.1 (verified `True`). It is kept as its own function because the plan's Interfaces block names it and because Pipecat's default dict shape is not contractually stable across versions; if it ever drifts, fix it here rather than at the call sites.
- **Task 13 (`handlers.py`):** `FunctionSchema` in 1.8 takes an optional `handler=` argument, and the LLM service auto-registers it for any `LLMContext` advertising the schema, so `register_function` is no longer required. `build_tools` deliberately leaves `handler` unset so the schemas stay pure data usable by the text driver and by promptfoo. If Task 13 prefers auto-registration over `register_tool_handlers`, attach handlers by copying the schemas — do not add a `handler` parameter to `build_tools`, or the Gemini path in Task 12 gets a non-serialisable field.
- **Tool argument contract for `dispatch_tool` (Task 12) and the voice handlers (Task 13):** `send_booking_link` requires only `service_id`; `capture_request` requires only `kind`; `request_appointment_change` requires `kind` and `contact`; `escalate` requires `reason`; `end_conversation` takes nothing. Everything else is optional and will simply be absent from the arguments dict — read with `.get`, never `[...]`. `contact.phone` is documented to the model as "leave empty on voice", so on voice the caller id from `ConversationRef` is the phone of record.
- `capture_request.kind` is `new_booking | callback | question | training_enquiry` and `request_appointment_change.kind` is `reschedule | cancel`; these are the tool-level vocabulary, and they are **not** the same set as `ItemDraft.type`. Whatever mapping Task 4's `ItemDraft` needs belongs in `dispatch_tool`, not here.
- `escalate.reason` is `human_request | clinical | complaint | payment | legal | unsure` — the full `EscalateReason` union. Note that `rules_gate` (Task 6) can only ever return the first four; `legal` and `unsure` reach the system exclusively through this tool, so `dispatch_tool` must handle them even though no lexicon produces them.
- **No free text anywhere.** Every top-level string parameter carries an `enum`; the only unconstrained strings are `contact.name/phone/email` and `preferred_window.date`, all nested inside objects and all contact/scheduling details rather than notes. `CLAUDE.md` non-negotiable 2 and the task's own `test_tools_have_no_free_text_parameters` both police this: adding a top-level string without an `enum`, or any sub-key to `contact`/`preferred_window` outside `name, phone, email, date, part_of_day`, fails the test. Do not add a `notes`, `details`, `summary` or `reason_text` parameter in any later task.
- The `service_id` enum is built from `cfg.services` at call time, so it is per-tenant and changes the moment a config version lands. `build_tools` takes the config and holds no cache; if Task 13 builds the tool list once per call that is correct, but anything longer-lived must rebuild after a registry cache expiry (`flows.md` §7 step 3).
- **Prompt wording is not tenant-editable and is deliberately not in `scripts.yaml`.** The HARD RULES block is instructions to the model, not anything a caller hears; per `CLAUDE.md` non-negotiable 3 the *spoken* fixed wording lives in `scripts` and is rendered by Task 5, never lifted from this prompt. The prompt tells the model to say nothing about a tool's result precisely because the renderer speaks it.
- `build_system_prompt` reads `cfg.knowledge` verbatim into the tail of the prompt (`tenant-config.md`: "goes into the cached system prompt verbatim", keep under 4,000 words). The whole prompt is stable for a given `(cfg, channel)` except for the one "Right now it is …" line, so it is the natural prompt-caching boundary for Task 12 — if you add caching, cache everything and let the clock line be the cache-busting suffix, or move that line into the first user turn.
- `channel` is a plain `str`, and only `"voice"` is treated specially (it selects the "spoken aloud" medium sentence). Every other value, including `"sms"`, `"chat"` and `"instagram"` in the text-channels plan, falls through to "a text conversation". That is intentional; do not add a Literal that later plans would have to widen.
- `prompt.py` imports `_clock` from `spatalk.brain.hours` — a private name crossing a module boundary, which the plan specifies so the prompt's clock wording matches `humanize_due`'s exactly ("7:30 p.m.", not "19:30" and not "7:30 PM"). If `_clock` is ever renamed or made public, this import must move with it; the task's test pins the rendered form.
