Deviations:
- **The transcript is a button that opens a drawer in place, not an href.** The plan asks for "a transcript link on the card (the conversation id is on the item)". There is no route that addresses one conversation: `ConversationsPage` opens a transcript by calling the `readConversation` *action*, deliberately an action and not a query because the runtime writes an audit row naming the reader on every read and a cached query would stop recording the second one (`portal/src/client/operations.ts`, comment above `readConversation`). A plain link would therefore have had to be a link to the conversations list, which does not start the follow-up from what was said. The card calls the same audited action and renders the messages in a right-hand drawer (`data-testid="request-transcript"`). Evidence: `portal/src/client/pages.wasp.ts` has `action(readConversation, orgEntities)` and no `/app/:orgSlug/conversations/:id` route.
- **That drawer is a second, smaller one rather than a component shared with `ConversationsPage`.** Extracting the existing drawer would have meant editing `ConversationsPage.tsx`, a file this task does not own, and reshaping a component whose block-number button, health note and "Requests from this conversation" list are pinned by `e2e-tests/tests/client.spec.ts` (`transcript-drawer`, `block-number`, `blocked-note`). The requests-page drawer carries only the header, the health-context note and the messages; blocking a number stays where it was.
- **The `Preferred` line is shown only when the caller actually named a day or a time of day**, although the plan lists it unconditionally. `preferred_text` is never empty — an item nobody was asked about renders as "any day" — so showing it always would put "Preferred: any day" on every escalation, which reads as something the caller said. `askedForATime(item)` tests the raw `preferred_window` for a `date` or `part_of_day` that is set and is not `"any"`. The summary sentence still says "Callback any day" on a booking or callback, exactly as the runtime composed it. This is the plan's own "no field shown when empty" applied to the one field whose text is never empty.
- **`#<id>` stays on the card.** "No raw ids" is read as the service id, which is gone. The item number is the handle staff already use — the owner's SMS says "front desk #7" and "Reply ACK 7" — so removing it would break the link between the text and the card.
- **The standalone type label is gone from the header**, because `summary` already opens with it ("New booking: …", "Callback: …", "CLINICAL question."). `itemTypeLabel` is still imported and used as the fallback in `summaryOf`, and `OverviewPage.tsx` still uses it, so nothing about that export changed.
- **`summaryOf(item)` falls back to `itemTypeLabel(item.type)` when `summary` is empty.** The running runtime has not yet been restarted with L1's code, so until the orchestrator restarts it the portal can read items with no `summary`; a headless card would be worse than the type label, and the fallback claims nothing the item does not say.
- **`e2e-tests/tests/client.spec.ts` was not touched.** The plan allows editing it "only if it pins the card layout"; it pins only the `request-row` count, the `acknowledge-<id>` / `resolve-<id>` testids and the "Requests" heading, all of which still hold. The Acknowledge and Resolve buttons kept their testids and their open-tab-only rendering; they simply share a wrapper with the Transcript button now.
- **Prettier is not clean on `RequestsPage.tsx`, and was not before this task either** (`npx prettier --check` on `git show HEAD:portal/src/client/RequestsPage.tsx` warns, as do the untouched `ConversationsPage.tsx` and `OverviewPage.tsx`). No CI step runs Prettier, so the file was left in the house style of its neighbours rather than reformatted, which would have churned lines this task did not change.
