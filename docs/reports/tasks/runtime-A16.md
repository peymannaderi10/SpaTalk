Notes for neighbours:
- **The `app` service runs one process, and it is the API, the job worker and the scheduler at once** (Task 14's `create_app(start_background=True)`). Scaling `app` to two replicas is safe for jobs (`FOR UPDATE SKIP LOCKED`) and for digests (guarded on `tenants.last_digest_date` in the same transaction), but it doubles the Silero and smart-turn model memory on an 8 GB box. The operations plan's separate-worker option is `start_background=False` on the API service plus a second service running the worker.
- **Migrations are a deploy step, never a container start-up step.** Nothing in the image runs `alembic upgrade head`; `docs/runbooks/deploy.md` runs it after `up -d --build` and again on every deploy. If the operations plan adds an entrypoint, it must stay idempotent and must not race two `app` replicas.
- **The image is 3.11 GB and roughly 2.7 GB of that is `nvidia-*` CUDA wheels pulled in by Torch, on a VPS with no GPU.** The clean fix is a CPU-only Torch (uv's `--torch-backend=cpu`, or the PyTorch CPU index), which changes dependency resolution and so belongs to the operations plan's hardening, not to a task whose Dockerfile the plan specified. Recorded here so nobody re-measures it.
- **Ports 80 and 443 are Caddy's, and only Caddy's.** The `app` service publishes nothing to the host; anything that needs to reach it from outside goes through a Caddy site block. The portal plan adds `app.` and `app-api.` hosts (`accounts-and-env.md` already names `APP_HOST` and `APP_API_HOST`), which means two more blocks in this Caddyfile and two more variables in `.env`; `test_caddyfile_proxies_both_hosts_to_the_app_container` asserts exactly two `reverse_proxy app:8000` lines, so whoever adds the portal blocks updates that assertion.
- **`media.<domain>` must stay DNS-only in Cloudflare.** Caddy proxies it to the same container as `api.`, so the split is entirely a DNS decision; the runbook's troubleshooting section names the silent-call symptom it causes.
