## How the router links the two services, in Pipecat terms

`LLMRouter` subclasses `pipecat.pipeline.parallel_pipeline.ParallelPipeline` with one branch per service, each branch laid out `FunctionFilter(DOWNSTREAM) -> service -> FunctionFilter(UPSTREAM)` with `filter_system_frames=True` and `enable_direct_mode=True`. Both filters close over the same predicate, `service is self._active`. That is Pipecat's own idiom for interchangeable services — `pipecat/pipeline/service_switcher.py::ServiceSwitcher._make_pipeline_definition` builds exactly this layout — and `ParallelPipeline` is what gives each branch its `PipelineSource`, its `PipelineSink`, `StartFrame`/`EndFrame`/`CancelFrame` synchronisation across branches, `setup`/`cleanup`, and `processors_with_metrics()`. `FunctionFilter._should_passthrough_frame` always passes `StartFrame`, `EndFrame` and `CancelFrame`, so both services are started and stopped with the pipeline whichever one is active.

Frame flow, per turn:

1. `LLMRouter.process_frame` sees the `LLMContextFrame` going downstream, remembers it, clears the per-turn failure set, and sets the active service from `breaker.active(*vendors)`. Then `ParallelPipeline.process_frame` queues the frame to **both** branches; only the active one's filter passes it, so exactly one service ever sees the turn.
2. Everything the active service pushes downstream (`LLMFullResponseStartFrame`, `LLMTextFrame`, `LLMFullResponseEndFrame`, the function-call frames, metrics) leaves its branch sink through `ParallelPipeline._pipeline_sink_push_frame` -> `_parallel_push_frame` -> `LLMRouter.push_frame`, which forwards it unchanged, so `OutputGuardProcessor` and the TTS downstream behave exactly as they did with the service in the pipeline on its own. An `LLMTextFrame` also records a success on the breaker: words came back.
3. A failure is an `ErrorFrame` travelling **upstream**, carrying `processor=<the service>` (`FrameProcessor.push_error` sets it; both `GoogleLLMService` and `BaseOpenAILLMService` push their completion failures through it, and neither marks itself unusable for a 503 — `ErrorCategory.SERVER.is_permanent` is False). It reaches the branch source, which is a `PipelineSource` bound to `_parallel_push_frame`, so it too arrives at `LLMRouter.push_frame`. The router records the vendor's failure, switches the active service, and re-queues the remembered `LLMContextFrame` into the other **branch** (`self._pipelines[i].queue_frame(...)`, not straight at the service) so the retry takes the same filter, the same queue and the same ordering a fresh turn takes. The error is swallowed: nothing downstream and nothing upstream hears about a failure that cost the caller one model call.
4. A second failure in the same turn finds the other service already in `_failed_this_turn`, so `push_frame` forwards the `ErrorFrame` upstream as usual and `PipelineWorker`'s `on_pipeline_error` runs — exactly one error per doomed turn.

`LLMRouter.register_function` forwards to both services, so `run_call` still calls `register_tool_handlers(llm, session)` once and both vendors can file the item the caller rang about.

## Deviations

- **`LLMRouter` is a `ParallelPipeline`, not a bare `FrameProcessor`.** The plan says "a `FrameProcessor` that links the two services as its own children" and tells the implementer to study how `ParallelPipeline` or `Pipeline` links processors. Hand-rolling the linking would have meant re-implementing `_setup_processors`, `_cleanup_processors`, lifecycle-frame synchronisation and the source/sink pair; `ParallelPipeline` is a `BasePipeline` is a `FrameProcessor`, so the interface the plan asked for is satisfied by inheritance. Evidence: `pipecat/pipeline/parallel_pipeline.py` and `pipecat/pipeline/base_pipeline.py` in the installed 1.8.1.
- **Pipecat's own `ServiceSwitcherStrategyFailover` was rejected, deliberately.** Two reasons, both in its source: `handle_error` returns `None` unless `failed_service.is_usable` is already False, which a 503 never causes; and nothing in `ServiceSwitcher` re-sends the context that failed, so the caller would still lose that turn to silence. The cooling-off decision also has to be the shared `VendorBreaker`, which the text channels read too. `LLMSwitcher` was rejected as well: it calls `_sync_registered_tool_handlers` on every member, which is `LLMService` API and would have forced the tests' fakes to impersonate a vendor service.
- **The output guard does not reset the failure count on `LLMFullResponseStartFrame`.** The plan says it should. `pipecat/services/openai/base_llm.py::process_frame` pushes `LLMFullResponseStartFrame` *before* the completion and pushes `LLMFullResponseEndFrame` in a `finally`, so a **failed** turn emits both frames around nothing at all; resetting the count there would zero it on every failed turn and `model_down` could never be reached. Instead the start frame sets `session.model_turn_open = True` and the count is cleared by an `LLMTextFrame` — the model actually saying something. `model_turn_open` is also what the plan's counter needs to work at all: two consecutive failed turns are normally less than `APOLOGY_INTERVAL_SECS` (10 s) apart, so without a per-turn marker the burst suppression would swallow the second turn's failure and the caller would loop apologies forever. `tests/test_llm_failover.py::test_a_turn_that_produced_no_words_does_not_clear_the_failure_count` pins this.
- **`apology_for_error` keeps its `TTSSpeakFrame | None` signature; `error_frames` is new.** The plan wants the `model_down` line "and the caller ended with an `EndFrame` after it". `apology_for_error` returns the `model_down` frame and sets `session.ended`; the new `error_frames` wraps it and appends `EndFrame()` when the session just ended, which is the same shape `on_idle_timeout` uses. Keeping the old signature keeps `tests/test_llm_resilience.py::test_a_model_error_is_answered_with_the_fixed_line_once_per_interval` intact and unweakened.
- **`make_llm` was split, and `llm_stage` added.** `make_llm_service(settings, model)` builds one vendor's service (and is where the addendum's `base_url` goes); `make_llm(settings)` returns the pair; `llm_stage(primary, secondary, settings)` returns the router, or the primary service itself when there is no secondary, so a runtime with no fallback runs yesterday's pipeline object for object. The plan names no function for that last step.
- **A fallback whose vendor has no key logs and yields `None` rather than raising.** The primary still raises `ValueError` at start-up as before (`test_selecting_a_vendor_without_its_key_still_fails_at_start_up_not_mid_call`). Half-configuring an optional feature must not take the phone line down.
- **`/healthz` reports vendor names, not model strings**, for `primary`, `secondary` and `active`; `breaker_open_until` is the ISO time the *primary* vendor will be tried again, or null. The plan's payload does not say which of the two it meant; the vendor is the fact an operator can act on and the model string is already in the deploy's env.
- **Files touched that the plan does not list**, all for the `make_llm` pair: `runtime/scenarios/voice/eval_bot.py`, `runtime/tests/test_qa_gate_a.py`, `runtime/tests/test_llm_thinking.py`. Also `runtime/spatalk/voice/session.py` (two fields) and `runtime/spatalk/http/app.py` (the `llm` block), which the plan implies but does not list.

## Notes for neighbours

- `Scripts.model_down` is a new tenant script with a default, and it was added to `runtime/tenants/skincentrix/scripts.yaml` and `docs/reference/tenant-config.md` (QA gate A asserts the three agree key for key). **The founder must re-import the bundle** for the tenant's stored config to carry it: `spatalk tenant import tenants/skincentrix`. Until then Skincentrix falls back to the schema default, which is the same sentence.
- The router absorbs the first `ErrorFrame` of a turn, so `on_pipeline_error` — and therefore `model_unavailable` — now fires only when every configured vendor failed the same turn. With no fallback configured that is unchanged behaviour.

## What the founder must set

To activate the failover, in `runtime/.env`, then restart the runtime:

```
LLM_MODEL_FALLBACK=openai:gpt-4.1-mini      # any vendor prefix; must be a DIFFERENT company from LLM_MODEL
OPENAI_API_KEY=sk-...                        # the key for whichever vendor the line above names
```

To choose (or change) a vendor in either slot: `LLM_MODEL=<prefix>:<model>` / `LLM_MODEL_FALLBACK=<prefix>:<model>`, where a bare name is Google and the prefixes are `openai:`, `openrouter:`, `deepseek:`, `xai:`, `groq:`, `together:`, `fireworks:`, `dashscope:` and `compat:`, plus that vendor's key (`OPENAI_API_KEY`, `OPENROUTER_API_KEY`, `DEEPSEEK_API_KEY`, `XAI_API_KEY`, `GROQ_API_KEY`, `TOGETHER_API_KEY`, `FIREWORKS_API_KEY`, `DASHSCOPE_API_KEY`, `COMPAT_API_KEY`). `compat:` also needs `LLM_COMPAT_BASE_URL`; every other vendor's host can be moved with `LLM_<VENDOR>_BASE_URL`. Optional tuning: `LLM_BREAKER_FAILURES` (3), `LLM_BREAKER_WINDOW_SECS` (60), `LLM_BREAKER_COOLDOWN_SECS` (300).

Leave `LLM_MODEL_FALLBACK` empty and nothing about a call changes.

Verify from outside the process: `curl -s https://api.spatalk.ca/healthz | jq .llm` should print the two vendor names and which one is answering.
