Deviations:
- Added `whatsapp_template_digest: str = "front_desk_digest"` to settings, which the plan's File Structure did not list, because the plan's Interfaces block requires the digest to use a `front_desk_digest` template outside the window and the other two template names are settings; hard-coding one of the three would have been the odd one out. Evidence: plan W1 Interfaces, "Digest: `digest.email` also sends the digest text to every whatsapp destination (template `front_desk_digest` outside the window, text inside)".
- Added `whatsapp_port(ctx)`: the production `DeliveryPort` (`HttpSlackEmailDelivery` / `SlackBotDelivery`) has no WhatsApp methods, so `deliver.whatsapp` uses `ctx.delivery` when it speaks WhatsApp (tests inject `MemoryDelivery`) and builds a `WhatsAppDelivery` from settings otherwise. Without this the job would have required every deployment to swap its delivery object. Evidence: `grep -n "class HttpSlackEmailDelivery" -A 3 spatalk/ledger/delivery.py` shows only `send_slack`/`send_email`.
- `WhatsAppDelivery.__init__` takes `graph=None` (the plan writes `WhatsAppDelivery(settings, graph: GraphClient)`). Passing a client positionally still works exactly as specified; None lazily builds an `HttpGraphClient` on `https://graph.facebook.com/{meta_graph_version}` with the access token, so production needs no wiring change.
- `Destination.address_env` also became legal for `kind: email` (validator now accepts `address` **or** `address_env`), which the plan's Interfaces block asked for; to make that field actually work, `schedule_item_delivery` now puts `to_env` on the `deliver.email` payload, `_deliver_email` resolves it, and the digest resolves it through `destination_address`. Without that resolution an email destination configured only by `address_env` would have enqueued `to: None`.
