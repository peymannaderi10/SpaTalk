## Tokens

`Main.css` now carries the kit's `:root` and `.dark` verbatim under the names the portal already used, plus `--chart-1..5` and the `--sidebar-*` family, plus `--radius: 0.625rem` and the `sm/md/lg/xl` radius scale. The names the portal had added on top of shadcn keep the values they had: `card-accent`, `card-subtle`, `secondary-muted`, `success`, `warning`, `destructive-foreground`.

One structural change came with them. The portal held tokens as bare HSL triplets and read them through `hsl(var(--x))`; the kit, and every refreshed registry component, holds whole colours read through `var(--x)`. The file is now on the kit's convention. This was safe to do in one move because `hsl(var(` appeared **only inside `Main.css`** — 36 occurrences, all of them in the file itself — so no component had to change.

The kit's base layer came too: `border-border outline-ring/50` on everything, thin scrollbars in the border colour, the pointer cursor on buttons, and the `faded-bottom` utility. The portal's own utilities (`no-scrollbar`, `chat-height`, `inbox-height`, the three gradients) and its extra scales (breakpoints, `text-title-*`, shadows, z-indexes) are all still there; the gradients had their `hsl(var(...))` rewritten.

Fonts: Inter, which is what the kit loads, but from `public/fonts` rather than Google's CDN — latin and latin-extended, upright and italic, variable across weights 100 to 900, four woff2 files totalling about 430 KB, with `public/fonts/OFL.txt`. `--font-sans` is declared in a plain `@theme` block (not `@theme inline`) so it is emitted at the root and Tailwind's preflight picks it up, and `body` also carries `font-sans` as a belt-and-braces.

## The component refresh, and what was kept

The shadcn CLI was run from WSL against `portal/components.json`. **The first run produced the wrong components** and had to be thrown away: `components.json` named `tailwind.config.cjs`, a file that does not exist, and a non-empty `tailwind.config` makes the CLI treat the project as Tailwind v3 and serve the v3-era registry — `React.forwardRef`, `displayName`, no `data-slot`, and a `sidebar.tsx` with zero `data-slot` attributes. Setting `"config": ""` (and `baseColor` to the kit's `slate`) got the v4 components the kit is built on. Evidence: `grep -c data-slot src/client/components/ui/sidebar.tsx` -> `0` before, `28` after.

Refreshed (17): alert, avatar, button, card, checkbox, dialog, dropdown-menu, form, input, label, select, separator, sheet, switch, textarea, accordion, progress.
Added (12 + a hook): sidebar, table, command, tooltip, badge, tabs, skeleton, breadcrumb, chart, scroll-area, popover, collapsible, and `hooks/use-mobile.ts`.

To find what the portal had customised rather than guess, a scratch project was built with the *old* `components.json` and the same component list pulled into it, so the portal's previous files could be diffed against pristine registry files instead of against the new ones. That showed the portal's files were already `data-slot`-era registry output run through `prettier-plugin-tailwindcss` — nearly every difference is class-order — and left exactly two real customisations:

- **`card.tsx` had a `cardVariants` cva** with `default`, `accent`, `faded` and `bento`. Restored on top of the new card: `accent` as it was, `bento` renamed **`subtle`** after the token it paints. `faded` is **dropped**, and this is the one thing that did not survive: it painted `text-card-faded-foreground`, a token no stylesheet in this repository has ever defined, and `grep -rl "card-accent\|card-subtle\|card-faded" src --include=*.tsx` finds no call site for any of the three. `cardVariants` is now exported.
- **`button.tsx` had `cursor-pointer`** in its base class string. Restored as the kit's own base-layer rule, `button:not(:disabled), [role="button"]:not(:disabled) { cursor: pointer }`, which keeps the behaviour and also covers the elements that only play a button.

Not refreshed, deliberately: **`toast.tsx` and `toaster.tsx`**. The registry has replaced them with sonner, and the portal's Radix pair carries a `position` prop that `App.tsx` passes. `git diff --stat` on both is empty.

`form.tsx`'s `aria-describedby` and `aria-invalid` are in the new version too, so nothing was lost there.

## Deviations

- **The kit has no breadcrumb component.** The plan lists `Breadcrumbs` among the things vendored from it. It is written here on the registry's `breadcrumb` primitives, in the kit's idiom, and takes its trail as data (`Crumb[]`) rather than parsing the route: the page knows the organisation's name and the request's number, and the shell should not have to reverse them out of a URL.
- **The kit has no empty state either.** `EmptyState` is written in the idiom of the kit's `ComingSoon` block — centred icon, heading, muted line — sized for a panel and with room for one action.
- **The kit's `use-table-url-state` and its bulk-actions bar are not vendored.** The hook is written against TanStack Router's typed search params and has no react-router equivalent to copy, so `DataTable` keeps sorting, filters and paging in local state; a page that wants them in the URL can lift them later. Nothing in this portal selects rows to act on them in bulk, so the bar has nothing to do.
- **The router swap.** Every `Link`, `useNavigate` and `useLocation` in a vendored file is react-router's. Two places needed more than a substitution: the kit's `checkIsActive` compares one `href` string that TanStack hands it, so `sidebar-nav.tsx` compares `location.pathname` and `location.search` separately and only insists on the query where several items share a path (`isActive`, exported so R1 can test it); and the kit's `CommandMenu` reads its open state back out of the search context, which would have made the two files import each other, so the provider passes `open`/`onOpenChange` down as props.
- **Icons are Tabler's in every vendored file.** The kit's data-table uses `@radix-ui/react-icons`, which the portal does not have; adding it for eleven glyphs when R3 moves the whole portal to Tabler would have been a dependency to remove again. `lucide-react` is untouched and still what `components/ui/*` imports.
- **`@tanstack/react-table` is pinned to `^8.21.3`.** `npm install @tanstack/react-table` resolves to `9.2.4`, which is a different API (`useTable`, `createTableHook`, a `legacy` entry point) that the kit's code does not compile against. 8.21.3 is the kit's line. `recharts` came in at `^3.8.0` — the version the registry's `chart` item asked for on the v4 registry, and the kit's line too.
- **Two dependencies arrived that the plan does not name**, both pulled in by the registry components: `radix-ui` (the unified package the current registry imports from, replacing the individual `@radix-ui/react-*` for everything except `toast.tsx`) and `cmdk` (the command palette). Per the plan, nothing was removed; the individual `@radix-ui/*` packages are still in `package.json`.
- **One page changed outside the token layer.** `src/admin/dashboards/analytics/RevenueAndProfitChart.tsx` painted its second legend swatch and label with `--secondary`, which under the kit's palette is near-white in light mode — the series would have vanished. Its three `secondary` classes are now `chart-2`. It is R3's file; this is a one-line rescue so no page is broken before it is restyled.
- **`head.wasp.ts` reads `BRAND`, which the task's list of exceptions did not anticipate.** The alternative was a third literal or dropping the product name from the meta description. It is safe because `brand.ts` imports nothing at all — the same shape as `src/server/mailFrom.ts`, which `emailSender.wasp.ts` already imports and which Wasp already evaluates at compile time. It was proved rather than assumed: `esbuild src/client/head.wasp.ts --bundle --platform=node --format=esm --external:@wasp.sh/spec` then importing the result prints the three head entries with the name interpolated.
- **The logo moved**, `src/client/static/logo.svg` -> `public/brand/logo.svg`, and `BRAND.logo` holds URLs rather than bundler asset imports. `brand.ts` has to stay import-free for the point above, and it is read by server code (`organizations/operations.ts`) where an SVG import would not survive. Both call sites — `NavBar.tsx` and `admin/layout/Sidebar.tsx` — now read `BRAND.logo.mark`. Git recorded it as a rename, so the file has one copy, not two.
- **`components.json` changed** (`tailwind.config` emptied, `baseColor` to `slate`). Without the first, the CLI serves v3 components, as above.
- **Prettier was not run**, following N2 and L2: there is no config file, no format script and no CI step, and `prettier-plugin-tailwindcss` would not load without one. The files the shadcn CLI wrote are in the registry's style (no semicolons); the files written by hand follow the repository's (double quotes, semicolons, two spaces).
- **`wasp build`, `wasp start`, `wasp test`, `wasp db` and `wasp compile` were not run**, as the plan requires. The stylesheet was validated with the standalone Tailwind v4 CLI and the types with `tsc` against `tsconfig.src.json` emitting to `/tmp`, never into `.wasp/`.

## Notes for R1

- **`nav.ts` is the model and nothing else** — no component imports it except the vendored `AppSidebar`, `SidebarNav` and `CommandMenu`, and none of those is mounted. `AppSidebar` takes `{ context: NavContext, header, footer }`: `header` is where the organisation switcher goes, `footer` where the user menu goes, and neither this file nor any other layout file imports Wasp, which is what keeps them testable.
- **The settings tabs are the one loose end.** `SettingsPage` holds its tab in `useState` today, with no query parameter. The Setup section models the eight tabs as eight items pointing at `/app/:orgSlug/settings?tab=hours` and so on, because R1 asks for them as sidebar items. Until `SettingsPage` reads and writes `?tab=`, every one of those items opens the page on Hours. `nav.test.ts` allows the settings route to appear more than once precisely because of this, and insists every other route appear exactly once.
- **`ROUTES_OFF_THE_SIDEBAR` is a contract, not a comment.** `/app/:orgSlug` and `/admin/tenants/new` are in it with reasons. A route added to the Wasp spec and put nowhere fails `nav.test.ts`; the fix is either a nav item or an entry there.
- **The testids are new**, since the old tab strip in `OrgShell.tsx` carried none to move: `nav-overview`, `nav-conversations`, `nav-requests`, `nav-settings-<tab>` (eight), `nav-billing`, `nav-people`, `nav-admin-dashboard`, `nav-admin-users`, `nav-admin-tenants`, `nav-admin-health`. Also `theme-switch`, `profile-menu`, `sign-out`, `command-palette-open`, `table-search`, `table-reset-filters`, `table-view-options`, and `<testId>-row` on `DataTable` rows.
- **`ThemeSwitch` uses the portal's `useColorMode`**, not the kit's cookie-backed provider, so there is one theme mechanism and it still writes `color-theme` to local storage and toggles `.dark` on `document.body`. It offers light and dark; the kit's third "system" choice would need `useColorMode` to grow one, which is not R0's.
- **`Main` and `DataTablePagination` use container queries** (`@7xl/content:`, `@2xl/content:`). They need `@container/content` on the element wrapping the content — the kit puts it on `SidebarInset`. Without it nothing breaks; the wide layouts simply never apply.
- **`Header` renders a `SidebarTrigger`**, so it has to be inside a `SidebarProvider`, and `Search` has to be inside a `SearchProvider`.
- **The palette has moved under every existing page.** `--secondary` was a saturated amber and is now the kit's light slate; `--primary` is the kit's dark slate rather than the brand navy. Paired usages (`bg-accent` with `text-accent-foreground`, and so on — 28 and 23 call sites) are fine by construction. The unpaired ones were counted: `text-primary` (9), `text-success` (3), one `text-secondary` and one `border-secondary`, the last two both in the admin revenue chart and both dealt with above. `BRAND.colors.primary` is `"var(--primary)"` on purpose — the palette lives in `Main.css` and the brand module points at it rather than holding a second copy.
- **Screenshots are still owed.** The plan makes light and dark screenshots of every page a done criterion, and they are the orchestrator's after `stop-portal.sh` / `start-portal.ps1`. The first thing to check in `wasp-start.log` is that the Wasp compiler was happy evaluating `head.wasp.ts` with its new import.
- **Not committed, and not this task's:** nothing. `portal/package-lock.json` was already modified in the working tree when this task started and is committed here, because the four installs rewrote it. Everything was staged by explicit pathspec.
