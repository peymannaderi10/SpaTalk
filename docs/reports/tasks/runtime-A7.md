Deviations:
- **The Postgres container is published on host port 5434, not 5432.** This machine runs two native Windows PostgreSQL services (`postgresql-x64-16`, `postgresql-x64-18`); the 16 service holds `0.0.0.0:5432`, so Docker only got `[::]:5432` and every host connection — IPv4 and IPv6 alike — landed on the native server, which has no `spatalk` role. Every DB call failed with `asyncpg.exceptions.InvalidPasswordError: password authentication failed for user "spatalk"` while the same credentials worked inside the container. Changing the published port is the smallest fix that does not touch the founder's own Postgres services (stopping them needs admin rights and would break whatever else uses them). Changed: `runtime/docker-compose.yml` `ports: ["5434:5432"]` (the container port and the in-network `db:5432` used by the deploy compose in Task 16 are untouched), and the matching defaults in `runtime/spatalk/settings.py`, `runtime/tests/conftest.py` and `runtime/.env.example`. All four are Task 1 files. CI is unaffected: the Task 15 workflow sets `TEST_DATABASE_URL`/`DATABASE_URL` explicitly and a GitHub runner has no native Postgres. Evidence: `Get-NetTCPConnection -LocalPort 5432 -State Listen` -> `0.0.0.0:5432` owned by pid 7960 `C:\Program Files\PostgreSQL\16\bin\postgres.exe` and `[::]:5432` owned by `com.docker.backend`; `docker port runtime-db-1` -> `5432/tcp -> 0.0.0.0:5432`; a probe as user `postgres` (a role the container does not have, since `POSTGRES_USER=spatalk`) returned `password authentication failed for user "postgres"` on both `127.0.0.1` and `::1`; after the remap, `asyncpg.connect(host='127.0.0.1', port=5434, ...)` -> `OK PostgreSQL 16.14 on x86_64-pc-linux-musl` (the container's build, not the native one).
- **`alembic/env.py` gained one line: `await connection.commit()` after `run_sync(do_run_migrations)`.** The plan's `do_run_migrations` runs `CREATE SCHEMA IF NOT EXISTS runtime` before `context.configure`, which opens the connection's transaction; `MigrationContext.begin_transaction()` is then a no-op (alembic leaves an already-open transaction to its caller), so the DDL was rolled back when the connection closed. Evidence: with the plan's body verbatim, `uv run alembic upgrade head` printed `Running upgrade  -> 0001, initial` with no error and the verification query from Step 5 printed `[]`; with the commit added the same query prints `['alembic_version', 'audit_log', 'conversations', 'items', 'jobs', 'messages', 'tenant_config_versions', 'tenant_numbers', 'tenants', 'usage_events']`, exactly the list Step 5 expects.
- **`TenantRegistry.import_config` does not call `self.invalidate(cfg.id)`.** The plan's Step 6 code calls it; the plan's own Step 1 test asserts the opposite (`assert (await reg.get("skincentrix")).name == "Skincentrix"  # cached` immediately after an `import_config` that renamed the tenant, then an explicit `reg.invalidate(...)` before the new name is visible). `docs/reference/flows.md` §7 step 3 settles it — "Registry cache expires within 30 s; the next call or message uses the new version" — and the reference wins over the plan. A write in one process cannot clear another process's cache anyway, so TTL expiry is the only honest contract. `invalidate()` is still public and is what C3's config-save path should call for its own process. Evidence: with the plan's `self.invalidate(cfg.id)` in place, `uv run pytest tests/test_registry.py -v` -> `1 failed, 1 passed`, `AssertionError: assert 'Skincentrix Beauty Bar' == 'Skincentrix'` at `tests/test_registry.py:26`; without it, `3 passed`.
- Minor: `alembic revision --autogenerate` was run with `--rev-id 0001` so the file lands at the path the plan names, `alembic/versions/0001_initial.py`, instead of a random hash slug. `alembic init -t async` also generated `alembic/README` and `alembic/script.py.mako`; both are committed as-is.

Notes for neighbours:
- **Everyone who touches the database on this machine:** the local Postgres is on **5434**, not 5432. `docker compose up -d db` from `runtime/` recreates the container with the new mapping (the `pgdata` volume and the `spatalk` / `spatalk_test` databases survive). If a fixture or command still says 5432 you will get `InvalidPasswordError`, not a connection refusal, because the founder's native PostgreSQL 16 answers there — do not read that error as "wrong credentials in the repo".
- **Task 8 (`PgLedger`):** `Item.id` is a plain `Integer` primary key, so Postgres assigns it from an identity sequence and the plan's `assert rec.id == 1` only holds because the `engine` fixture does `drop_all` + `create_all` per test, which restarts the sequence. Keep using that fixture rather than truncating tables. `Item` has no free-text column and must never gain one (`CLAUDE.md` non-negotiable 2, and `data-model.md` says so explicitly). `preferred_window` is `JSONB` defaulting to `{}` — write `{"date": ..., "part_of_day": ...}` there, never a sentence. The partial index `ix_items_breach` is `(due_at) WHERE state = 'open' AND escalated_at IS NULL`, so `breached(now)` should filter on exactly those two predicates to use it.
- **Task 9 (jobs) and Task 10 (scheduler):** `Job` and `AuditLog` tables already exist here — do not re-declare them; import from `spatalk.models`. `Job.state` is `queued | done | dead` with `ix_jobs_state_run` on `(state, run_at)` for the `FOR UPDATE SKIP LOCKED` claim query. `Tenant.last_digest_date` is a `Date` (tenant-local day, per `data-model.md`) and is where the digest de-duplication belongs.
- **Task 13 (voice) and B2 (text channels):** `end_conversation` takes `health_context` as a fifth, defaulted parameter — the plan's Interfaces line omits it but its Step 7 code has it, and `flows.md` step 11 requires the health flag to be persisted at finalize. `append_message` silently drops empty/whitespace-only text, so a barge-in that produced no words will not create a blank transcript row. `latency_ms` is stored as a JSONB list; `stage_ms`, `last_message_at`, `closed_at`, `followup_sent_at`, `external_session`, `slack_channel` and `slack_ts` are **not** columns yet — `data-model.md` assigns them to B2, B5 and E5, so those tasks add them by migration on top of `0001`.
- **Anyone adding a migration:** `Base.metadata` carries `schema="runtime"`, `env.py` uses `include_schemas=True` and `version_table_schema="runtime"`, and the `alembic_version` table lives in `runtime` too. Autogenerate compares against `DATABASE_URL` (the `spatalk` database), not `TEST_DATABASE_URL`; the test suite never runs migrations, it builds the schema from the models, so a model change that is not migrated will pass the tests and fail on deploy. Run `uv run alembic upgrade head` after every model change.
- `record_usage` accepts `qty: float` into a `Numeric(14,3)` column, so values come back from Postgres as `decimal.Decimal`. Cost aggregation in E9 should sum in `Decimal`, not float.
- `TenantRegistry.import_config` upserts `tenant_numbers` from `cfg.voice_numbers` and `cfg.sms_from_number`, but `tenant_numbers` is authoritative (`tenant-config.md`) and the Skincentrix bundle ships both empty — the number rows come from `add_number` / `spatalk numbers add` (Task 14), and re-importing the bundle will not delete a number added that way.
