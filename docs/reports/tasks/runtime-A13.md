Notes for neighbours:
- **Task 14 — `run_call(websocket, token, ctx)` is the whole `WS /ws/{token}` handler.** It calls `websocket.accept()` itself, so the FastAPI route must *not* accept the socket first. It also calls `verify_stream_token` before accepting, so an expired or forged token raises `itsdangerous.SignatureExpired` / `BadSignature` out of the route; catch it there and close with a policy-violation code rather than letting it 500. `run_call` blocks for the whole call and runs `_finalize` in a `finally`, so the route should await it directly.
- **Task 14 — `ctx` must carry `sms`.** `run_call` calls `load_capabilities(cfg, ctx.ledger, ctx.sms, ctx.clock)`; `JobContext.sms` defaults to `None`, and Tier C's `send_booking_link` will call `sms.send(...)` whenever the tenant has an `sms_from_number` and the caller has a phone. `build_context` should set `sms=TelnyxSms(settings.telnyx_api_key)` (the class this task added in `spatalk/sms.py`) or the first booking-link call on a live tenant raises `AttributeError` inside `dispatch_tool` and degrades to the `refuse_unavailable` script.
- **Task 14 — mount `spatalk.voice.texml.router` and put the context on `app.state.ctx`.** `texml.py` reads `request.app.state.ctx` for `registry`, `sf` and `settings` only. It needs `settings.secret_key` and `settings.media_ws_host`; `media_ws_host` is a bare host (`media.test`), the `wss://` and `/ws/` are added by the route.
- **The TeXML loop guard is not implemented here, by design.** `flows.md` §1 step 2 assigns it to E1 (operations plan). Today an inbound call from one of our own numbers resolves normally. When E1 adds it, the check belongs at the top of `texml()`, before `start_conversation`, and speaks `scripts.loop_guard`.
- **The unknown-number response is the one sentence in the voice path that is not tenant config.** `"This number is not configured."` is hard-coded in `texml.py` because no tenant resolved, so there are no `scripts` to render from. Every other utterance in this task comes from `render()` or `render_script()`.
- **`RulesGateProcessor` ends the call through `session.worker`, not by pushing an `EndFrame` downstream.** It pushes only the `TTSSpeakFrame` and then calls `session.worker.queue_frames([EndFrame()])`, so the goodbye is actually spoken before the pipeline drains. `session.worker` is assigned after the `PipelineWorker` is built; if a future caller forgets to assign it, the script is still spoken and the call simply does not hang itself up. The same contract holds for `handlers.py` on `end_conversation`.
- **`RulesGateProcessor` swallows the `TranscriptionFrame` on a gate hit.** It sits *before* the user aggregator precisely so the gated sentence never enters `LLMContext` and no LLM completion runs. Do not move it after `user_agg`, and do not call `Brain.turn` from the voice pipeline (see the Task 12 report) — Pipecat's `GoogleLLMService` is the only thing that may run a completion on this path.
- **`RulesGateProcessor` mutates `session.ref` when health context is volunteered** (`self._s.ref = self._s.ref.model_copy(update={"health_context": True})`), so the flag sticks for the rest of the call and reaches `end_conversation(..., health_context=session.ref.health_context)` in `_finalize`. That is the persistence step the Task 12 report asked the channel adapters to own. `ConversationRef` is frozen; the rebinding is on the session, not the model.
- **`OutputGuardProcessor` re-frames every sentence.** It buffers `LLMTextFrame`s, splits on `(?<=[.!?])\s+`, and emits one *new* `LLMTextFrame` per complete sentence, stripped. Downstream TTS therefore sees whole sentences, not token fragments, and the original frames are consumed. A blocked sentence sets `_dropping`, so the rest of that response is discarded rather than half-spoken — the caller hears exactly one `cannot_complete` sentence and nothing else from that turn. `InterruptionFrame` and `LLMFullResponseStartFrame` both reset the buffer and the drop flag.
- **The guard's blocked path files a real `capture_request(kind="question")` item before speaking**, same as `Brain.turn`. `session.guard_blocks` counts them and `_finalize` logs the count. Anything that reuses this processor must not suppress that capture; `CLAUDE.md` non-negotiable 1 holds only because the filing really happens.
- **Band bookkeeping is the Task 12 rule, duplicated in `handlers.py` as that report instructed:** `3` for an `escalation_*` capture, otherwise `max(band, 2)`; the rules gate sets `3` outright and the guard sets `max(band, 2)`. `LinkSent` and `Refused` leave the turn at band 1.
- **`register_tool_handlers(llm, session)` registers the same closure for all five names in `spatalk.brain.tools.TOOL_NAMES`** and dispatches on `params.function_name` inside `dispatch_tool`. Adding a tool to `TOOL_NAMES` without adding a branch in `dispatch_tool` yields `Refused(reason="out_of_scope")`, not a crash. Every result callback sets `FunctionCallResultProperties(run_llm=False)`: the rendered sentence is final and the model never gets to paraphrase what happened.
- **`UsageObserver` reads `MetricsFrame.data`, so `PipelineParams(enable_metrics=True, enable_usage_metrics=True)` is load-bearing.** It accumulates into `session.usage["llm_input_tokens" | "llm_cached_tokens" | "llm_output_tokens" | "tts_chars"]`, which `_finalize` writes as six `usage_events` rows (telephony seconds, STT seconds, TTS chars, and three token units) plus `end_conversation`. `TurnLatencyObserver` measures `UserStoppedSpeakingFrame` -> `BotStartedSpeakingFrame` in ms, which is the brief's S7 number; it is deliberately wall-clock and per-turn, so a call with no completed turn contributes no samples and `_finalize` logs no percentiles.
- **A cold-process timing flake to know about, not a bug in this code.** `pipecat.tests.utils.run_test` waits at most `start_timeout=1.0 s` for the pipeline to start. On the very first `PipelineWorker` in a fresh interpreter on this Windows machine, one run of `test_guard_replaces_completion_claim_and_drops_rest` exceeded that and raised `TimeoutError` from `asyncio.timeouts`. It passed on every rerun (the file alone, the four files together, and the full suite twice), because by then the worker machinery is warm. The tests were left exactly as the plan wrote them. If CI (Task 15) sees it, the fix is `start_timeout` on the `run_test` call, not a change to any assertion.
