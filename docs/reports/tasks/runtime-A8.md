Notes for neighbours:
- **Task 9 (delivery, action pages, Slack interactions):** `on_created` is awaited **after** the insert transaction has committed, and it receives the detached `spatalk.models.Item` ORM row plus the `TenantConfig` — so `item.id` is already assigned and it is safe for the callback to open its own session (that is what `schedule_item_delivery` needs). The session factory is built with `expire_on_commit=False`, so every attribute of a returned `Item` stays readable after the session closes; do not add `expire_on_commit=True` anywhere.
- **Task 9 signing:** `sign_action` takes the secret as its **first positional argument** (`sign_action(settings.secret_key, item.id, "ack", tenant_id)`); it does not read `Settings` itself, so nothing in `spatalk.ledger.links` imports settings or the database. The salt is the constant `"item-action"` — a token signed with any other salt will not verify. `verify_action` raises `itsdangerous.SignatureExpired` (a subclass of `BadSignature`) past `max_age_seconds`, default 7 days, which is the `/a/{token}` window in `api-surface.md`; catch `BadSignature` to cover both.
- **Task 9 and Task 10 state machine:** `acknowledge` and `resolve` are idempotent and return the row unchanged when the transition does not apply (a second `acknowledge` on an already-acknowledged item returns it still `acknowledged`), and both return `None` for an unknown id — so an action page or a Slack button can distinguish "no such item" from "already done" without a second query. `resolve` on an item still `open` back-fills `acknowledged_at`/`acknowledged_by` with the same actor, so a one-click resolve never leaves a resolved item that was never acknowledged. Neither writes an `audit_log` row: `flows.md` §2 step 4 puts the audit write on the staff action path, so Task 9's handlers own it.
- **Task 10 (scheduler):** `breached(now)` filters on exactly `state = 'open' AND due_at < now AND escalated_at IS NULL`, matching the partial index `ix_items_breach` from Task 7, and orders by `due_at`. `mark_escalated(item_id, now)` only stamps `escalated_at`; it does not change `state`, so an escalated item stays `open` and keeps appearing in `list_open` until a human acts — and it drops out of `breached()` immediately, which is what makes the escalation fire once. `list_open(tenant_id)` deliberately includes `acknowledged` items (an acknowledged item is still owed), so the daily digest should filter further if it wants only untouched ones.
- **Due times:** `create_item` computes `due_at` through `BusinessCalendar(ref.tenant).due_for(draft.urgency, clock.now())` — urgent is wall-clock `escalation.urgent_minutes`, normal is `escalation.standard_business_hours` business hours in the tenant timezone. Nothing else may compute a due time (`CLAUDE.md` non-negotiable 8). `owner` is snapshotted from `ref.tenant.escalation.owner_email` at creation, so editing the tenant config later does not move existing items to a new owner.
- **`items` still has no free-text column and must never gain one.** `ItemDraft` is the only way in and its fields are fixed (`CLAUDE.md` non-negotiable 2). `preferred_window` is written as `draft.preferred_window.model_dump()`, i.e. `{"date": ..., "part_of_day": ...}` — never a sentence.
- `PgLedger` imports nothing from `spatalk.brain.outcomes`, so the Tier C structural-honesty grep stays clean when the voice pipeline wires the ledger in at Task 13.
