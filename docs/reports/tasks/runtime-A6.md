Deviations:
- `guard.py`'s `_pattern` sorts the alternation **shortest-first** (`key=len`) where the plan wrote `key=len, reverse=True`. The plan's own test asserts `matched == "booked"` for `"Great, I've booked you in for Thursday at 2."`, but Python's `re` picks the first alternative that matches at the leftmost position, not the longest, so a longest-first alternation reports the longer `"booked you"` and the plan's test fails on the plan's implementation. Sorting the other way is the smallest change that reconciles them, and it cannot change whether text is blocked — the `(?<![\w-])`/`(?![\w-])` lookarounds enforce the word boundary and the engine backtracks through the alternation regardless of order, so only the diagnostic `matched` string differs. Evidence: `uv run python -c "..."` over the same four terms printed `longest-first matched: booked you` / `shortest-first matched: booked`. `rules.py` keeps the plan's `reverse=True`, since no rules assertion reads `matched` and longer phrases are the more useful diagnostic there.
- `rules.py` imports `EscalateReason` under `if TYPE_CHECKING:` rather than at runtime. `spatalk/brain/requests.py` is Task 4's file and had not landed after roughly ten minutes of waiting (`ls spatalk/brain/` showed only `__init__.py`, `guard.py`, `hours.py`, `rules.py`; `git log --oneline` topped out at Task 3's `fb51a2b`), so the plan's literal `from spatalk.brain.requests import EscalateReason` made all seven rules tests fail with `ModuleNotFoundError: No module named 'spatalk.brain.requests'` for a reason that has nothing to do with this task. `from __future__ import annotations` is already in force, so `GateDecision.reason: EscalateReason` and `ORDER: list[EscalateReason]` are stored as strings and never evaluated; the annotations, names and signatures are byte-for-byte what the plan specifies, and ruff still resolves the name (no F821, no F401). Evidence: before the change `uv run pytest tests/test_rules.py -q` -> `7 failed` with that `ModuleNotFoundError` at `spatalk\brain\rules.py:19`; after, `uv run pytest tests/test_guard.py tests/test_rules.py -v` -> `11 passed` and `uv run ruff check spatalk tests` -> `All checks passed!`.

Notes for neighbours:
- **Task 4 owner / orchestrator:** the `TYPE_CHECKING` guard in `rules.py` is a race workaround, not a design choice. Once `spatalk/brain/requests.py` exists and exports `EscalateReason`, the four-line block can collapse back to the plan's plain top-level import with no other edit. Until then a rename of `EscalateReason` in Task 4 will **not** fail loudly here — nothing evaluates the annotation at runtime and there is no type checker in this stack (ruff is configured `select = ["E4","E7","E9","F"]`, no mypy). If Task 4 renames it, grep `rules.py` by hand.
- `ORDER` is `["human_request", "clinical", "complaint", "payment"]` and deliberately omits `"legal"` and `"unsure"`, two members of Task 4's `EscalateReason` union. `"legal"` phrases (`lawyer`, `sue`, `legal action`) currently resolve to `complaint`, and `"unsure"` has no lexicon at all because it is a model-side decision, not a lexical one. Task 11/12/13 must not assume `rules_gate` can ever return those two reasons.
- The gate is **first match wins by position, then by `ORDER`**: for each reason in turn the whole utterance is scanned, so `"I want to speak to a person about a rash"` gates as `human_request`, not `clinical`, even though `rash` appears later. That ordering is intentional (an explicit request for a person outranks the topic) and Task 13's `RulesGateProcessor` should not re-rank it.
- `rules_gate` and `health_context_mentioned` are two separate questions and must both be asked on every final transcription (`docs/reference/flows.md` step 8). A gate hit ends the turn with fixed wording; a health-context hit only sets `conversations.health_context` / `items.health_context` to true. The matched phrase itself must never leave this module — it is a diagnostic, and `CLAUDE.md` non-negotiable 2 forbids putting it on an item. Do not log `GateDecision.matched` into anything a staff-facing view renders.
- `guard()` returns the **whole replacement string**, not a redacted sentence: when it blocks, `text` is exactly the `replacement` the caller passed. Task 13 should pass `render_script("cannot_complete", ...)` (Task 5) as `replacement` so the caller hears tenant wording rather than a stub. Guard sentence-by-sentence per `flows.md` step 9, so one bad sentence does not discard a whole good turn.
- `has_completed=True` short-circuits before any matching, so a Tier A/B integration that really did book something can say so. Tier C never sets it — `CLAUDE.md` non-negotiable 1 keeps `Completed` out of `tier_c.py` entirely, so in this plan the flag is always `False` in practice. Task 15's structural-honesty test should assert that.
- Both lexicons are additive only: `DEFAULT_COMPLETION_LEXICON + cfg.lexicons.completion` and `DEFAULT_LEXICONS[reason] + cfg.lexicons.<reason>`. A tenant can widen a gate but cannot remove a built-in term, which is what `docs/reference/tenant-config.md` requires ("a tenant cannot remove one"). The Skincentrix bundle's `payment: ["financing", "skinc club"]` is what makes `test_tenant_additions_apply` meaningful.
- Matching is case-insensitive and hyphen-aware: the boundary class is `[\w-]`, not `\w`, so `"post-treatment"` in the Skincentrix clinical additions will not match inside `"post-treatment-free"`, and `"rebooked"` does not trip `"booked"`. Anyone adding a term with an internal hyphen gets that behaviour for free; anyone adding a term with a trailing hyphen will find it never matches.
- `_pattern` recompiles on every call. At voice turn rates that is irrelevant, but Task 15's promptfoo suite and any future bulk transcript scan should hoist it if they call these functions in a tight loop.
