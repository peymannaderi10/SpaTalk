## Findings

- [blocking] **The runtime suite is red on a clean checkout, and CI is red with it.**
  `runtime/tests/test_internal_api.py::test_the_packaged_rates_match_the_researched_table`
  compares `runtime/spatalk/rates.json` (what `/internal/rates` serves the portal) with
  `docs/research/rates.json` (what the cost model reads). Three entries exist only in the
  researched file: `/reference_bundles_usd_per_min/telnyx_voice_ai_agents_all_in`,
  `/tts/soniox_tts`, and the `/voice_stacks/"B4 Soniox only (STT + TTS), single vendor"`
  stack. The researched file moved on in `12fc7b8` and `a0939cc`/`4fbee36`; the packaged copy
  has not been touched since `7267613`. So the portal quotes cost numbers from a table the
  research no longer agrees with, and `.github/workflows/ci.yml`'s runtime job — which runs
  `uv run pytest -q` unfiltered — fails on every push. Five task reports (E4, E5, E6, E7, E9)
  recorded it as "not mine" and routed it to a rates owner who has not picked it up. It is
  one command to fix (`cp docs/research/rates.json runtime/spatalk/rates.json`, after
  checking the three entries are wanted) and it is the only thing standing between this gate
  and a pass. Reproduce: `cd runtime && uv run pytest -q tests/test_internal_api.py -k rates`.
- [major] **The deployed runtime image is 10.1 GB, and 5.2 GB of that is CUDA.**
  `docker compose build app` produces `runtime-app:latest` at 10.1 GB;
  `du -sh /usr/local/lib/python3.12/site-packages/*` inside it gives `nvidia 3.2G`,
  `torch 1.1G`, `triton 894M`, `llvmlite 172M`, `transformers 54M`. They arrive through
  `pipecat-ai[…,silero,local-smart-turn,…]` in `runtime/pyproject.toml`, which resolves
  `torch` from PyPI's default (CUDA) wheels. The target is an OVH VPS with a CPU and no GPU,
  and `docs/runbooks/deploy.md`'s update path is `git pull && docker compose up -d --build`,
  so every deploy rebuilds and stores that. The CPU wheel of torch is about 200 MB: a
  `--extra-index-url https://download.pytorch.org/whl/cpu` (or dropping the extra that pulls
  it, if smart-turn is not used) is a one-line change in the Dockerfile. Not blocking —
  nothing about the product is wrong — but it will be felt on the first deploy.
  Reproduce: `cd runtime && docker compose build app && docker images runtime-app`.
- [major] **The portal end-to-end suite cannot seed a runtime that runs from the runtime's
  own virtualenv.** `portal/e2e-tests/global-setup.ts` runs `uv run python seed_runtime.py`,
  and `uv run` re-syncs `runtime/.venv` before running, which fails with `os error 32` while
  `spatalk.exe` from that venv is the live server the suite is about to test — the arrangement
  `portal/e2e-tests/README.md` itself documents for Windows. The failure is in `globalSetup`,
  so no test runs at all. `--no-sync` fixes it; the README's `RUNTIME_SEED_COMMAND` escape
  hatch is what QA used. Suggested fix: make the default `uv run --no-sync python …`, which
  is also what CLAUDE.md's runtime commands use. Reproduce: start the runtime with
  `runtime/.venv/Scripts/spatalk.exe serve`, then run `npx playwright test` in
  `portal/e2e-tests`.
- [major] **The conversation regression suite cannot be run to completion on this key, so
  nobody can say it is green.** The Google AI Studio free tier allows 20
  `generateContent` requests a day for `gemini-2.5-flash`, and one full pass of
  `runtime/scenarios/promptfooconfig.yaml` needs 30 provider calls plus a judge call per
  rubric. Three runs today (engineer A, engineer B, this gate) each reached the cap and
  returned a different partial set: 11/30 answered in run B, 10/30 here, no assertion failure
  in either. `.github/workflows/ci.yml` runs the same suite whenever `GOOGLE_API_KEY` is set,
  so CI will report errors on every push for a reason that has nothing to do with the code.
  Three ways out, none of them QA's to choose: put the key on the paid tier (the suite is
  about 30 short calls, cents per run), split the suite across nights so a day's budget
  covers a third of it, or run it against a second vendor now that `LLM_MODEL=openai:<model>`
  exists. Until then, treat promptfoo results as spot checks, not as a gate.
  Reproduce: run the command in the promptfoo section twice in one day.
- [minor] **Running the portal's own test commands rewrites the committed
  `portal/package-lock.json`.** After `wasp build`, `wasp test client run` and
  `npx playwright test` (the last two with `PORTAL_EMAIL_PROVIDER=Dummy`, as
  `playwright.config.ts` sets), `git status` showed `portal/package-lock.json` modified with
  `nodemailer` removed: Wasp generates the server's dependency list from the email provider
  it was told to compile, and npm rewrites the lock to match. So the lock file in the
  repository records whichever provider was used last, and any developer who runs the
  end-to-end suite gets a dirty tree — or, worse, commits a lock file that a production
  `wasp build` then has to undo. QA restored the file (`git checkout -- portal/package-lock.json`).
  Reproduce: `wasp build`, then `wasp test client run`, then `git diff --stat portal/package-lock.json`.
- [minor] **A bare `npx tsc --noEmit` fails in `edge/sms-worker` on a clean checkout**, with
  60 errors of the `Cannot find name 'Request'` kind, because `tsconfig.json` includes the
  generated `worker-configuration.d.ts` and that file is gitignored. The package's own
  script (`npm run typecheck` = `wrangler types && tsc --noEmit`) exits 0. Gate B recorded
  the bare command as passing; it passed there only because the generated file already
  existed on that machine. Nothing to fix in the worker — but the bare command should not be
  quoted as the typecheck.
- [minor] **`docs/reference/api-surface.md`'s portal line does not name
  `PORTAL_EMAIL_PROVIDER`**, which Wasp bakes into the build (`Dummy` for development and
  the end-to-end run, SMTP for production, and `wasp build` refuses `Dummy`). Everything
  else in `portal/.env.server.example` is listed. The founder fills the VPS from that
  reference. Task C1's other reference complaint — `SMTP_USER`/`SMTP_PASS` against Wasp's
  `SMTP_USERNAME`/`SMTP_PASSWORD` — has since been resolved: the portal line reads `SMTP_*`
  and the `SMTP_USER`/`SMTP_PASS` row is tagged `A`, the runtime, where those are the right
  names.

## Tests added

`runtime/tests/test_qa_gate_c.py` — four tests, none of which duplicate an existing one:

- `test_alembic_head_and_the_orm_metadata_describe_the_same_schema`. The suite builds its
  schema with `Base.metadata.create_all` and production builds it with `alembic upgrade
  head`; nothing compared them, so a model column added without a migration passed every
  test and would fail on the VPS. Two throwaway databases, one built each way, diffed on
  `information_schema.columns` (type, nullability, length, precision) and on `pg_indexes`
  definitions. Currently identical. Seen failing: with a `qa_gate_c_drift` column appended to
  `Conversation.__table__` in memory it reports
  `columns the models declare that no migration creates (missing revision?):
  [('conversations', 'qa_gate_c_drift', 'character varying', 'YES', 8, -1, -1)]`.
- `test_every_job_kind_has_a_handler_in_the_server_process`. Handlers register as an import
  side effect, so a job kind whose module `spatalk.http.app` never imports would be queued
  nightly for ever and never run, silently. The check runs in a subprocess that imports the
  app and nothing else (the registry is process-global; `tests/test_jobs.py` registers a
  `test.fail` handler of its own) and pins the fourteen kinds. Seen failing: with three
  invented kind strings it reported `queued nightly, never run: ['instagram.event',
  'messenger.event', 'meta.token_refresh']`.
- `test_the_scheduled_ops_jobs_are_enqueued_under_the_kinds_their_handlers_registered`.
  The four nightly and monthly ops jobs, enqueued by `ledger/scheduler.py` under the same
  `RUN_KIND` their handlers registered.
- `test_the_cost_model_runs_and_exits_zero_on_the_researched_rates`. `python
  docs/research/costmodel.py docs/research/rates.json` is one of the commands CLAUDE.md
  names and no test ran it. Seen failing on a wrong expected heading.
