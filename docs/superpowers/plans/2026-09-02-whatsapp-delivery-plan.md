# WhatsApp Delivery Implementation Plan

> **For agentic workers:** contract level: files, exact interfaces, behaviours, tests. Tests first. Founder decision 2026-09-02: Slack is parked; tracked items go to staff on WhatsApp (Meta WhatsApp Cloud API), with Acknowledge and Resolve as reply buttons. Email delivery stays.

**Goal:** Every tracked item and every escalation reaches the tenant's staff numbers on WhatsApp within seconds, with two reply buttons that acknowledge or resolve the item, and the daily digest arrives the same way. Nothing generated by a model is ever sent to staff; the message is built from the item's structured fields exactly like the Slack blocks were.

**Architecture:** A `whatsapp` destination kind on the tenant's delivery config, a `WhatsAppDelivery` implementation of the existing `DeliveryPort` shape (send text, send interactive buttons, send template), a `deliver.whatsapp` job kind, and a Meta webhook (`/whatsapp/webhook`) that reuses the Instagram plan's verify-token and HMAC-SHA256 checks and turns button replies into `ledger.acknowledge` / `ledger.resolve` calls, replying with a short confirmation. Business-initiated messages outside Meta's 24-hour customer-service window must use an approved template; inside the window free-form text and interactive buttons are allowed. The implementation sends interactive buttons when the window is open (a staff reply within the last 24 h) and the approved template otherwise, then records the window.

**Spec:** `docs/superpowers/specs/2026-09-01-ai-front-desk-architecture-design.md` §3 (ledger delivery), §5 (no free text; nothing generated). Depends on the runtime plan Tasks 8 to 10 and the Instagram plan D2 (webhook verification helpers).

## Global Constraints

- Everything in the runtime plan's Global Constraints. Staff messages are built from item fields and `docs/reference/tenant-config.md` wording only; never from model output.
- Personal phone numbers are not committed: a WhatsApp destination references an environment variable name (`address_env`) that holds the E.164 number, exactly like Slack webhooks reference `webhook_env`.
- Button payloads are signed tokens from `sign_action(secret, item_id, action, tenant_id)`; a click is honoured only if the token verifies and the sender's number is one of the tenant's configured WhatsApp destinations or `staff_phone_numbers`.
- All Meta calls go through the existing `GraphClient` port with the fake in tests; no live Meta call in tests.
- The 24-hour window rule is enforced in code, not assumed: a send outside the window uses the template path or is queued with a clear job error, never a silent drop.

## Task W1: WhatsApp destination, delivery and buttons

**Interfaces:**
- `Destination(kind="whatsapp", address_env="SKINCENTRIX_WHATSAPP_STAFF")`; validator: whatsapp needs `address_env`; email accepts `address` or `address_env`.
- `WhatsAppDelivery(settings, graph: GraphClient)` with `async send_text(to: str, body: str) -> str` (returns message id), `async send_buttons(to, body, buttons: list[tuple[str, str]]) -> str` (id, title; max 3, title max 20 chars), `async send_template(to, template, lang, body_params: list[str], button_params: list[str]) -> str`. Posts to `/{phone_number_id}/messages` with `messaging_product: whatsapp`.
- `MemoryDelivery` gains `whatsapp: list[tuple[str, str, list]]` and the three methods.
- `build_whatsapp_text(item, cfg, links, now) -> str`: same lines as `_summary` plus the transcript link; under 1,024 characters.
- `build_whatsapp_buttons(item, links) -> [("ack:<token>", "Acknowledge"), ("resolve:<token>", "Resolve")]` where the tokens come from `links.ack_token` and `links.resolve_token` (already on `ActionLinks`).
- `schedule_item_delivery(sf, item, cfg, escalation=False)`: for each `whatsapp` destination enqueue `deliver.whatsapp` with `{item_id, tenant_id, to_env, escalation}`; urgent and escalation items go to every whatsapp destination regardless of `urgent_only`.
- Job `deliver.whatsapp`: resolve `to` from `os.environ[to_env]` (skip with a warning if unset); if `whatsapp_windows` shows an inbound from `to` within 24 h, `send_buttons`, else `send_template` with the item's type label, who, due wording and the transcript link as parameters and the two quick-reply buttons carrying the tokens; record usage `wa_out`.
- Digest: `digest.email` also sends the digest text to every whatsapp destination (template `front_desk_digest` outside the window, text inside).

**Tests:** destination validation; text builder under 1,024 chars and containing who, type label, due wording, transcript link, health-context line when flagged; buttons carry signed tokens and titles; scheduling enqueues one job per whatsapp destination and always for urgent; the job uses buttons inside the window and the template outside it (window row inserted by the test); missing env skips with a warning and no exception; usage row written.

**Done when:** tests pass, migration applies, suite green. Commit `feat(delivery): whatsapp destination with acknowledge and resolve reply buttons`.

## Task W2: WhatsApp webhook and button replies

**Interfaces:**
- `GET /whatsapp/webhook`: `hub.mode=subscribe` and `hub.verify_token == settings.whatsapp_verify_token` → echo challenge, else 403.
- `POST /whatsapp/webhook`: HMAC-SHA256 over the raw body against `whatsapp_app_secret` (and `facebook_app_secret` if set) via the same helper the Instagram router uses; 401 on mismatch; dedup by message id in `meta_events` (provider `whatsapp`); enqueue `social.wa_event` per message; 200 fast.
- `parse_whatsapp_payload(body) -> list[WhatsAppEvent(kind: "button"|"text"|"status", from_number: E.164 with plus, message_id, text, button_id, timestamp)]` for `entry[].changes[].value.messages[]` with `type` in `button` (template quick reply: `button.payload`), `interactive` (`interactive.button_reply.id`), `text`; statuses ignored but stored.
- Handler `social.wa_event`: record `whatsapp_windows(tenant, from_number, now)` for any inbound; for `button` with payload `ack:<token>` or `resolve:<token>`: `verify_action` → if the sender is a configured destination number or in `staff_phone_numbers` for that tenant → `ledger.acknowledge/resolve(item_id, actor=f"whatsapp:{from_number}")`, audit row, reply `send_text` "Item #<id> acknowledged/resolved." → else reply "This number is not registered as staff." For free text from a registered staff number that starts with `#<item_id>`: same relay semantics as the staff SMS path (`takeover.relay_from_staff`) if that module exposes it; otherwise reply the help text. Unknown sender: ignore.
- Tenant resolution: by `metadata.phone_number_id` matching `settings.whatsapp_phone_number_id` (one platform number for all tenants at MVP) and then by which tenant's destinations or staff list contains the sender; if none, ignore.

**Tests (fixtures in `tests/fixtures/meta/whatsapp_*.json`):** verify handshake; bad HMAC 401; duplicate ignored; template quick-reply button with a valid ack token acknowledges and replies; interactive reply button resolves; token for another tenant or a tampered token is refused with the "not registered" reply and no state change; unregistered sender ignored; inbound text records the window so the next delivery uses buttons; status events stored and ignored.

**Done when:** tests pass; `docs/reference/api-surface.md` lists the endpoint and payload shape; `docs/runbooks/whatsapp-setup.md` written (below). Commit `feat(social): whatsapp webhook with acknowledge and resolve replies`.

## Runbook content for `docs/runbooks/whatsapp-setup.md`

1. Meta app (the same app the Instagram plan uses; create it if it does not exist yet: developers.facebook.com → My Apps → Create → Business). Add product **WhatsApp**.
2. WhatsApp → API Setup: note the **test phone number** and its **Phone number ID** (`WHATSAPP_PHONE_NUMBER_ID`). Under "To", add the founder's own WhatsApp number as a recipient and confirm the code WhatsApp sends. Up to five recipients on the test number, no business verification needed.
3. Generate a **temporary access token** (24 h) for the demo (`WHATSAPP_ACCESS_TOKEN`). For anything longer: Business Settings → System Users → create one with WhatsApp permissions → generate a permanent token.
4. App Settings → Basic → App Secret (`WHATSAPP_APP_SECRET`, same value as `FACEBOOK_APP_SECRET`). Choose a random `WHATSAPP_VERIFY_TOKEN`.
5. Webhooks → WhatsApp → Callback URL `https://<host>/whatsapp/webhook`, verify token, subscribe to `messages`. (During a local demo the host is the tunnel hostname; re-verify when it changes.)
6. Message templates (WhatsApp Manager → Message templates): create utility templates `front_desk_item` (body: "{{1}} via {{2}}. Who: {{3}}. Due {{4}}. Transcript: {{5}}" with two quick-reply buttons "Acknowledge" and "Resolve") and `front_desk_digest` (body "{{1}}"). Approval is usually minutes for utility templates. Until approved, send the founder's number a WhatsApp message to the test number first ("hi"): that opens the 24-hour window and the runtime uses free-form text with buttons.
7. `.env`: `SKINCENTRIX_WHATSAPP_STAFF=+1<founder number>`, plus the four variables above. Restart `spatalk serve`.
8. Test: `uv run spatalk items list skincentrix` after a demo call shows the item; the WhatsApp message arrives with two buttons; tapping Acknowledge updates the item and replies a confirmation.

## Self-review against the spec

- Delivery to a channel staff already use, one tap to acknowledge or resolve, escalation on every channel: W1.
- No free text and nothing generated: messages are built from item fields and fixed wording; the model is never involved (W1).
- Security: signed button tokens, sender allow-list, HMAC on the webhook, dedup (W2).
- Compliance: Meta as a subprocessor (already in the register for Instagram); personal numbers by env reference only.
